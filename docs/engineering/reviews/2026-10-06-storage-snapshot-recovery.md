# Storage snapshot and disposable recovery acceptance

This slice covers SB-04 and the database/file fixture portion of SB-05. Complete application recovery remains unproven. The executable fixture is `lab/disposable-recovery-drill.py`; this document is an acceptance record, not a fixture dependency.

## Snapshot admission

The original implementation exported database rows, then copied the current tenant file tree. Temporary-file reproductions showed both a deleted object and a same-length replaced object could still receive a complete manifest. The new implementation imports the exported PostgreSQL snapshot when reading `storage.objects`, checks every referenced native UUID version path against the archived file size and quoted MD5 content fingerprint, and writes the manifest only after admission. Deleted or changed referenced objects refuse. Extra unreferenced versions are allowed.

The contract is restricted to the pinned native file backend with its default slash version separator. Native mtime ETags, missing content fingerprints, missing UUID versions and unsupported metadata refuse explicitly. Existing mtime-configured objects can therefore make backups fail; no automatic metadata migration or runtime configuration change is included. Hostile same-version volume writes and deliberate MD5 collisions are outside this contract. MD5 is the native content fingerprint, not a cryptographic guarantee of equality against chosen collisions. SHA-256 binds each completed archive after capture.

The archive captures native Linux MIME, cache-control and ETag attributes as PAX metadata. Restore applies those attributes and preserves nanosecond modification times, permissions, UID and GID. Missing filesystem attribute support refuses rather than silently discarding the supported metadata. Existing legacy archives without PAX attributes retain their previous limitations.

## Disposable fixture contract

Run from a public clone with Python 3.12 or newer, the public `cryptography` package, and a Linux Docker daemon. No private installation state or owner workstation is needed. The locked DB and Storage images must already be available locally; admission does not pull images. Source-only checks use temporary files and do not require Docker.

```sh
python3 -m unittest discover -s lab -p 'test_backup*.py'
python3 -m unittest discover -s lab -p 'test_restore*.py'
python3 -m unittest discover -s lab -p test_disposable_recovery_drill.py
python3 lab/disposable-recovery-drill.py plan --output recovery-plan.json
python3 lab/disposable-recovery-drill.py run --output recovery-evidence.json
python3 -m unittest discover -s lab -p test_disposable_storage_backup_drill.py
python3 lab/disposable-storage-backup-drill.py plan --output storage-plan.json
python3 lab/disposable-storage-backup-drill.py run --output storage-evidence.json
```

The fixture owns uniquely named disposable resources and private temporary state. It publishes no ports, uses no network, and runs at most one test container at once. Database limits are 512 MiB and 0.5 CPU; helper limits are 256 MiB and 0.5 CPU. It stops its DB while executing the original pinned Storage helper, then restarts its DB. It never uses the retained runtime or unrelated resources.

The fixture seeds actual PostgreSQL schemas, tables, enums, functions, views, triggers, grants, RLS, database settings, scoped roles and memberships, versioned files and tenant metadata. It creates the shipped backup archives and seals recovery material through `recovery_bundle.py`. It deletes the source DB container and source DB/object volumes before restoring into fresh target resources. Restoration uses the existing fenced `backup.restore_storage`, `backup.restore` and explicit recovery paths. It tests interrupted cutover and recovery after reopening without losing new writes, plus scoped DB credential rotation and rejection of old passwords. Operator settings and JWT material are fixture data, not proof of actual application configuration or HTTP token invalidation.

The independent envelope key is required. Wrong-key decryption refuses. The envelope is bounded to 32 MiB and is a rehearsal transport; large backups continue to use the existing streaming offsite subsystem.

Enabled features outside the fixture's admitted inventory refuse before allocating resources. Auth, REST and Storage HTTP, pre-export signed URLs, Realtime, Functions, Vault, cron, queues, webhooks, logical subscriptions, external object stores, S3/TUS/Iceberg and management identity recovery remain unproven. Minimal fixture `auth` and `storage` schemas are not the official service migrations. Stopped writer descriptors exercise admission and cutover barriers, not live service readiness. These limits keep complete SB-05 open.

## Original Storage HTTP fixture

`lab/disposable-storage-backup-drill.py` uses ordinary service-role upload, overwrite, deletion and download requests against the pinned Storage image. It uses the original GoTrue migrations to create canonical Auth tables, removes GoTrue, then starts Storage with its original MD5 ETag default. It does not set an ETag override or edit native object metadata. It records actual metadata, version paths, file SHA-256 and native xattrs. Both adversarial HTTP changes occur after native `pg_dump` while the exported snapshot remains held. Acceptance requires a coherent checkpoint or explicit refusal before manifest publication. The ordinary backup is restored through the shipped fenced path and checked through a native HTTP download.

This fixture uses an owned internal bridge without published ports. PostgreSQL and Auth, then PostgreSQL and Storage, each run at 256 MiB and 0.25 CPU, for at most 512 MiB and 0.5 CPU combined. Each file helper runs alone at 256 MiB and 0.5 CPU. The fixture stops Storage and its DB during file helpers, then restarts only services that were running before the helper. Fenced Storage stays stopped until the existing restore path reopens it. These pauses are fixture resource coordination and interrupt test service availability; the backup implementation itself does not pause Storage. This test does not establish uninterrupted service availability, end-user Auth, signed URLs, cross-tenant isolation, full fresh-host application recovery, platform-secret rotation or enabled-feature recovery.

## Pinned identities and evidence

The reference is official Supabase `self-hosted/v0.8.2`, commit `564eab8ad7840b13324f68b1bfac074ef8d51c21`, tag object `47111f95a43ffcc20ab288e29c48ce0b80174bd6`, from `deploy/verify/reference_bundle.py`. Candidate DB is `public.ecr.aws/supabase/postgres:17.6.1.166`, manifest `sha256:b3bfedb107413abb3b8cb0d0874b0414a1dceb3d55bc0c778de6ad22d1f7dc86`. Candidate Storage is `public.ecr.aws/supabase/storage-api:v1.73.1`, manifest `sha256:c24fb33cc2fa38d0f9582a30312907fc56da333fb9ba0646833186197e4982f3`. The fixture records all six candidate image lock hashes. This identifies the frozen reference; it does not establish an executed comparison of official application stacks.

Native file path and ETag behavior were checked against [the pinned backend source](https://github.com/supabase/storage/blob/v1.73.1/src/storage/backend/file.ts) and [the pinned version adapter](https://github.com/supabase/storage/blob/v1.73.1/src/storage/backend/adapter.ts). [Supabase's backup documentation](https://supabase.com/docs/guides/platform/backups) separately identifies Storage object bytes as outside database backups.

Source regression evidence: both deletion and same-length replacement tests failed against the imported baseline because it published manifests. Both passed after admission was added. Actual temporary-file round trips verify supported attributes, timestamps, modes and ownership. An independent critic found loss of file modification time in the initial extraction change; the fix was independently rerun against file and directory metadata.

The final actual disposable DB/file run completed 32 checks with no failure in 512.123 seconds, within the 600-second limit and under the stated resource caps. It seeded a distinct preexisting target write and proved that exact value survives the first-rename rollback. It also proved post-reopening writes and trigger effects survive explicit recovery. Its source DB and object volumes were deleted before fresh target restore; every owned resource was removed and Docker inventories were checked afterwards. Evidence is in `docs/evidence/disposable-recovery-drill-2026-10-06.json`. The first two runtime attempts refused and cleaned their resources. The second exposed a missing target tenant directory and a first-rename assertion that could accept an earlier interruption; both were fixed before the earlier 31-check successful run. Independent review then required a preexisting target marker to prove original-write preservation during rollback. A later run refused during source setup and cleaned up. Temporary bootstrap probes demonstrated that the privileged-role check can succeed while native DB health is still starting; the exact prior SQL failure cause remains unproven. The fixture now requires exact locked image and owner, running state without OOM, native healthy status and the privileged-role check. Four source tests discriminate these readiness states. The separate original Storage HTTP run completed 18 checks with no failure. Ordinary uploads produced quoted MD5 metadata without an ETag override. Both native HTTP snapshot races changed live object state and refused before manifest publication. The shipped restore returned the original native HTTP bytes, metadata, UUID version and supported xattrs. All owned container, volume and network inventories were empty after cleanup. Evidence is in `docs/evidence/disposable-storage-backup-drill-2026-10-06.json`. This native HTTP execution predates the fixture-only DB readiness tightening; its report retains the executed source identity, and the backup/restore component hashes remain unchanged. The source and DB/file checkpoints are accepted at the final source identity. Independent source and runtime reviews and exact source bindings are embedded in `docs/evidence/storage-snapshot-recovery-2026-10-06.json`. Source tests alone do not establish application recovery, concurrent Storage HTTP behavior, full SB-05 acceptance or production readiness.
