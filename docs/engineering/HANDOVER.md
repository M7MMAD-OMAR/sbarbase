# In-place handover of the console process

Recorded 2026-10-23, revised six times the same day after six rounds of independent reviews, and on 2026-10-24 for R7 as built (the stop sequence) and the external database listener (the map at the end says where each of their findings is closed). Status: built behind `SBARBASE_HANDOVER`, off by default; unit and two-process tests only, not yet run on a server or in a container (the live gate). The section "As built" at the end lists where the build differs from this design. Part of [upgrades without an outage](plans/2026-10-23-upgrades-without-outage.md), phase 2, requirement R8. It depends on the kept runtime (phase 1, `lab/kept_runtime.py`), the versioned control stores (`release_channel.stores_changed`) and R7, which is committed (c4abd11): the graceful stop of the console process, `SO_REUSEPORT` on every fixed listener and the hold scoped to management. Nothing here is production ready, and nothing in it has been measured end to end; the measurements cited are of the kernel and Bun mechanisms it stands on.

## Why

With the owned containers kept across an upgrade restart (phase 1), what still stops every application is the Bun process `lab/upstream-server.ts`: it is the gateway, the console, the direct database listener and the Studio and Edge Functions Storage listeners, all in one. Today the supervisor stops it, exits 42 (`RESTART_FOR_UPGRADE`), and the service manager starts the new version after `RestartSec=10`. Nothing listens on the console port meanwhile.

The process cannot outlive the supervisor. Under systemd, when the main process exits the unit stops and the rest of its control group is killed (`KillMode=mixed`); under Docker the `sbarbase` container exits with its main process. So for a code-only release the supervisor does not exit: it replaces its own program with the new version's (`execve`, same process id, same unit, same container). The old Bun process, its child, keeps serving until the new one has passed a health round on a private port, joined the shared ports and been given every new connection; only then does the old one drain and exit.

Steering needs no special permission: `SO_ATTACH_REUSEPORT_CBPF` is an ordinary `setsockopt` on a socket the caller owns, and a classic BPF program needs no capability. Docker's default seccomp profile (moby `profiles/seccomp/default.json`) allows `setsockopt` without conditions; it is `pidfd_getfd` that it gates behind `CAP_SYS_PTRACE`, which is why the first draft's supervisor-side attach could not work in the container and the candidate attaches the program itself. The supervisor's checks only read `/proc/<child>/fd` and `/proc/net/tcp{,6}`, which a process may do for its own children of the same user without any capability. The last measurement shows that at this client rate R7's grace alone already avoided resets; steering is what makes that independent of the rate and of how long the old event loop is blocked (the queued-connection measurements above: about 20 of 40 reset without it, 0 with it). None of this was run inside a container here (the run rules forbid starting one); the Docker rehearsal in Tests must show it before the switch is used there.

## The switch

`SBARBASE_HANDOVER=1` in the supervisor's environment turns the handover on. `deploy/host-preflight.sh` adds it to its list of plain scalars. Under systemd it is a drop-in `Environment=SBARBASE_HANDOVER=1` line. In the container it must cross three places: `compose.yaml` gains `SBARBASE_HANDOVER: ${SBARBASE_HANDOVER:-}` under the `sbarbase` service's `environment:`; `deploy/compose.sh` passes it through its `exec env -i` list as `SBARBASE_HANDOVER="${SBARBASE_HANDOVER-}"`, beside the other declared inputs (it loads no `.env` and refuses `COMPOSE_FILE` overrides, so nothing else can carry it); and `docs/guides/docker.md` (with its Arabic sibling `docs/guides/docker.ar.md`) lists it under Settings with the command form `sudo SBARBASE_HANDOVER=1 deploy/compose.sh up`. The release that adds the `compose.yaml` line changes `compose.yaml`, so it is class `rebuild` and installs the old way, under Docker as under systemd (Q4); the container hands over only on upgrades after it, as Q6 already requires a running version that declares the protocol. Unset or any other value: off. Off, every code path is today's: no condition is evaluated, no record is written, the Bun process installs no new handler and writes no new file, the hold and snapshot keep today's order, and `lab/dev.py` handles signals where it does today. The switch must be on in the version being left (it decides) and the environment carries it across the `execve`.

**Scope: systemd and the container.** Both deployments hand over, by the same mechanism: the candidate steers its own listeners (H3), and the supervisor only reads `/proc` to check the groups. The container's own start gates run at B4 and B7 in their container form.

## When it is used

The old supervisor decides, in `Supervisor.update_finished`, at the point where it sets `restart_for_upgrade` and `keep_runtime` today. `handover.qualifies()` returns a plan only when every condition holds; any exception inside it counts as a condition that does not hold. Without a plan the exit is today's (exit 42, kept runtime), so a condition that fails costs nothing.

- **Q1.** The switch is on, the job is `apply` (an upgrade; a rollback, an automatic way back and an update check never hand over) and it completed: `status == 0 or self.moved_for_good('apply')`, the condition under which today's code keeps the runtime.
- **Q2.** A service manager runs this supervisor (`SBARBASE_GUARDED == '1'`), no stop was asked for (`asked` is not set), and no `cutover-operation.json` exists. These are the conditions under which `leave_runtime` records the kept runtime; Q10 checks that it did.
- **Q3.** The target declares the same protocol: `git show <to>:lab/handover.py` exists, its `PROTOCOL` line, read as text, equals this module's `PROTOCOL`, the hash on that protocol's line of its `FORMATS`, read as text, equals this module's `FORMATS[PROTOCOL]`, and `git show <to>:src/control/handover-formats.json`, parsed as JSON, declares every key this version's file declares, required and optional, with the identical declaration (type, required or optional, meaning); it may only add optional keys. The old Bun reads optional keys on the routing path (`realtime` in `lab/upstream-app.ts` about line 104, `storage` and `functions` in `lab/upstream-server.ts` about lines 121 and 122), so a change of any declared key is refused here, not only a change of a required one. So even a release that edited `FORMATS` in place, past the test, is refused here and installs the old way.
- **Q4.** The release is code only. `.lab/upgrades/state.json`, read as JSON without importing `lab/upgrade.py` (which the move replaced), has `phase` `applied`, `moved` true, `to` equal to `HEAD`, `from` equal to the commit this supervisor started on, and `changes` empty. Then, with this version's `release_channel` (imported when the supervisor started): `list(release_channel.pin_diffs(from, to))` is empty, `release_channel.classify(from, to)[0] == 'safe'`, and `release_channel.stores_changed(from, to)` is false. When the state carries `release.class`, it must also be `'safe'`. A class that is missing from the recomputation, unknown, wrong or not `safe` is no handover. This excludes every pin change (migrating or not), every release that changes the TLS proxy, the unit, `compose.yaml` or the image (class `rebuild`), every data migration (`manual`) and every control store schema change. It does not exclude a change of a container's computed settings, nor what `installation_runtime.py up` does to kept containers on every start (`Runtime.resume` stops each environment's REST unless `SBARBASE_ROLLING_SERVICES` names `rest`, `launch` replaces a container whose computed environment changed, `ensure_connection_capacity` may restart PostgreSQL, unadopted containers are retired): that is why B8 to B9 hold the whole of application traffic.
- **Q5.** The console port is pinned: `SBARBASE_CONSOLE_PORT` is set and not `0`.
- **Q6.** The running version declares the protocol: the old Bun is `self.server`, alive (`child_status(self.server) is None`), and both `server.json` and `listeners-<pid>.json`, read as JSON, name its pid with `protocol` equal to `PROTOCOL`. Since the old Bun was started from this version's code, the first release that carries the protocol is installed the old way; only upgrades from it hand over.
- **Q7.** The old Bun's group is clean: for every listener in its record, `/proc/net/tcp` and `/proc/net/tcp6` together hold exactly one socket in state `0A` (listen) at that address and port, and its inode is one of the old Bun's descriptors (`/proc/<pid>/fd/*` reading `socket:[<inode>]`).
- **Q8.** Steering works on this host: the old supervisor opens two `SO_REUSEPORT` listeners on an ephemeral loopback port, attaches the program to the second through `setsockopt` on its own descriptor, connects once and checks that the second accepted it, then closes both. This proves the kernel and the seccomp profile allow it, under systemd and in the container alike (the candidate is a child under the same profile). Q7 has already proved that `/proc/<old>/fd` can be read.
- **Q9.** There is room for two Bun processes: `MemAvailable` in `/proc/meminfo`, and where this process's cgroup has a `memory.max` other than `max` also `memory.max` minus `memory.current`, are each at least the old Bun's `VmRSS` plus `MEMORY_MARGIN_MIB`.
- **Q10.** `leave_runtime(origin)` recorded the runtime for the next start (A3). Q10 is checked in `main`'s `finally`, the others in `update_finished`.
- **Q11.** No `.lab/upstream/handover-failed.json` names this `to`. A handover that failed once for a commit is never tried again for it: the next move to that commit takes today's exit 42 at once.
- **Q12.** The start will build nothing: with this version's `console_build_check` (imported at start), `is_fresh(out=STAGED)[0]` (the build the upgrade child staged is fresh for the moved checkout, and B9's `adopt_staged()` puts it in place) or `is_fresh()[0]` (`.lab/ui` is already fresh). A build (`bun run build:ui`, which the module's own comment puts at a few hundred MiB) beside two Bun processes has no admission, so a release that needs one takes today's exit 42.

## What this needs from R7

R7 is being built at the same time (cp4). H8 and B8 rely on the following; the switch must stay off until each exists and is tested. As the working tree has it when this was revised:

1. Present: on `SIGTERM`, `drain()` keeps accepting for `ACCEPT_GRACE_MS` (300, `src/http/local-server.ts`) before the listeners close, and the database proxy does the same. Without the grace, the connections queued on the old Bun at H8 would be reset even with steering, because steering only stops new ones from arriving.
2. Present: `draining` (`connection: close` on every answer) is set at the signal and Realtime sockets are closed at the signal (`front.retire`); quiet kept-alive connections close at the end of the grace, after `settled()` (bounded by `SETTLE_MS_MAX`, 1000 ms), each from the inner end after its last answer (flush bounded by `PIPE_FLUSH_MS`, 5000 ms).
3. Present: a second `SIGTERM` finishes at once (`stopOnSignals`).
4. Present: every fixed listener binds with `reusePort`: a `Bun.listen` front for the console, Studio internal and Functions Storage, a `node:net` server for the database proxy and the external database listener; the hold scope `management` is an allowlist of the tenant data plane and an unknown scope is the full hold (`holdScope`).
5. Present: the answer caches of `upgradeHoldScope` (`src/gateway/hold.ts`) and `confirmationProbe` (`src/gateway/hold-bypass.ts`) count on `performance.now()`, a monotonic clock. A wall clock stepped back by S seconds would keep a cached "no hold" for about S + 1 s, longer than `HOLD_SETTLE_SECONDS`; a version that declares `PROTOCOL` must keep the monotonic clock.

## The sequence

### In the old supervisor (`lab/dev.py`)

- **A1.** `update_finished` calls `handover.qualifies(self)` (Q1 to Q9, Q11 and Q12). With a plan it stores it on `self.handover`; in every case it sets `restart_for_upgrade`, `keep_runtime` and `stop_event` as today.
- **A2.** `Supervisor.run`'s `finally` stops every child as today (scheduler, update child, backup, Studio, sign-in, Data API and toggle children, then the worker) except `self.server` when `self.handover` is set. It removes `supervisor.json` as today (its `pid` is this process's). The old Bun keeps serving; `server.json` keeps naming it.
- **A3.** `main`'s `finally` computes `keep` as today and calls `close_runtime(started or held, keep, origin, before_stop=...)`. With a plan, `before_stop` is `lambda: terminate_group(plan.server)` and the plan is dropped. `close_runtime` calls `leave_runtime(origin)` first when `keep` is true; only when the runtime was not left (`keep` false, or `leave_runtime` returned false: Q10) does it call `before_stop()`, so the old Bun is stopped and reaped, and only then `kept_runtime.discard` and `installation_runtime.py stop`. The runtime is never stopped under a serving Bun. Without a plan `before_stop` is `None` and `close_runtime` is today's.
- **A4.** The `with` block ends: `supervisor.lock` and `worker.lock` are released by closing them. Every descriptor Python and SQLite open is close-on-exec (PEP 446, `O_CLOEXEC`), so the new program inherits the standard streams and nothing this supervisor opened.
- **A5.** From here to A8 every exception goes to A9. With a plan, in the main thread (asserted; `execve` ends every other thread, and a child forked from another thread would get its `PR_SET_PDEATHSIG` signal, measured above; the old Bun was forked from the main thread by `Supervisor.run`): `signal.pthread_sigmask(SIG_BLOCK, {SIGTERM, SIGINT})`.
- **A6.** Then `asked` is checked. A stop that arrived before the mask was handled by the existing handler and set it; one arriving after is held pending. If set, the exec is cancelled: the mask is lifted, `terminate_group(plan.server)` stops and reaps the old Bun, and the process exits 42 exactly as today (the kept runtime record stays, as for any stop that arrives after the record).
- **A7.** `child_status(plan.server)` must still be `None`. The record `handover.json` is written with the old Bun's pid and start time; a write that fails (disk full, permission) raises `OSError` and goes to A9. From this moment the old Bun stops opening and closing fixed listeners (its timers check, every 2 s, whether `handover.json` names its pid, and rewrite its listener record with `frozen: true`).
- **A8.** `sys.stdout` and `sys.stderr` are flushed, then `os.execve('/usr/bin/python3', ['/usr/bin/python3', str(ROOT / 'lab/dev.py')], env)` with `env` the current environment plus `SBARBASE_HANDOVER_EXEC=1`. `SBARBASE_GUARDED` stays `1`: `leave_runtime` reads it as the proof that a service manager will start the next version, and removing it would make the next upgrade (and every later one) stop the owned runtime.
- **A9.** If anything from A5 to A8 raises (the record write, `execve` itself), the mask is lifted, `handover.json` removed, `terminate_group(plan.server)` stops the old Bun, and the process exits 42: today's planned restart with the kept runtime record in place.

### In the new program, up to the candidate

The process id, the unit, the container, the parent of the old Bun and the signal mask are the same; handlers are reset to default by `execve`, and a stop sent meanwhile is pending.

- **B1.** The first statements under `if __name__ == '__main__':`, only when `SBARBASE_HANDOVER_EXEC` is `1`: pop it from `os.environ`; install the `SIGTERM` and `SIGINT` handlers (moved out of `main` into module level, setting the module's `asked` and `stop_event`, which `main` then uses); then `signal.pthread_sigmask(SIG_UNBLOCK, {SIGTERM, SIGINT})`, before any child starts. - **B2.** `retiring = handover.adopt()`: reads `handover.json`. It is valid only with the exec marker, `protocol` equal, `to` equal to `HEAD`, and a `pid` whose `/proc/<pid>/stat` names this process as parent and whose start time equals `started`. Valid: a `handover.Retiring` for that pid, used for the rest of the start. A record that is present but not valid: if its pid is a live child of this process with the matching start time, it is stopped and reaped (`Retiring.end()`, B13) and the start goes on as an ordinary gated start; the record is removed either way. A start without the exec marker finds a record only after its unit or container ended, so its pid is gone or is not this process's child: it removes the record. A record whose pid is alive with the matching start time and is not this process's child means a handover is in progress under another process (a terminal start between A4 and B6, when no lock is held): that start refuses (`SystemExit('A handover of the console process is in progress')`) before it takes any lock, so it never removes a live record or joins the console port's group.
- **B3.** Everything below runs inside `try ... finally: retiring.end()` at module level, so an exit from the profile check, the guard or anything else before `main`'s own handling never leaves the old Bun serving under a process that is going away.
- **B4.** Host admission, before the guard, as the service manager orders it ("Read-only host admission precedes every lock, upgrade or runtime cleanup effect"): `docker_profile.require_or_exit()` as today; then under systemd (`SBARBASE_CONTAINER` not `1`) `deploy/host-preflight.sh --runtime`, in the container `/usr/local/lib/sbarbase/docker_profile.py check` and `docker_profile.py runtime $PWD`. A refusal is W5: nothing of the new version ran, no attempt is open, and today's restart then meets the same refusal in its own `ExecStartPre` or start script.
- **B5.** `run_guard()` runs the guard even though `SBARBASE_GUARDED` is `1` (the exec skipped the unit's `ExecStartPre` and the container script's guard), with `SBARBASE_GUARD_WAIT=0` as a terminal start does: a stuck guard exits at once, B3 ends the old Bun, the process exits, and the guard that the service manager runs on the following starts keeps its `STUCK_WAIT` of 300 s between them. So this process never sleeps 300 s with a stop unanswered; a stop that arrives while the guard works (a move back runs `bun install`) waits for it, as a stop waits for an `ExecStartPre` guard today, within `TimeoutStopSec=150`. A terminal start (no `SBARBASE_GUARDED`) keeps today's terminal mode exactly. When the guard returns 0 and `.lab/upgrades/state.json` (read directly) has a pending phase, `attempt_open` is set: the guard opened an attempt that this process must close if it stops cleanly (W4) or withdraw (W5). On the first start of a version the guard opens the attempt and cannot restore a snapshot (a restore needs `attempted_at`, which only `before_start` of the new version writes), so the old Bun having the stores open is harmless here. When the guard moves the checkout back, `run_guard` raises `SystemExit(42)` and B3 stops the old Bun first.

With `settle` false the order stays today's (snapshot, then hold).

Idempotent: once reaped it never signals that id again.

### Probe, promote, steer, retire, confirm (`handover.Promotion.poll`, once per supervisor turn)

`Promotion.poll()` replaces `Confirmation.poll()` and is called where it is today, every 0.25 s turn of `Supervisor.run`. Nothing in it blocks the loop: probe rounds and the verification requests run in `upgrade_health.background` threads, `/proc` reads and socket options take microseconds, and every wait is a check of a deadline on the next turn. Each turn of `Supervisor.run` calls `self.check()` before `self.confirm.poll()` (`lab/dev.py`, the `while not self.stop_event.wait(.25)` loop), and `check()` raises `RuntimeError('Local API exited; ...')` when `child_status(self.server)` is not `None`. In a handover start `check()` changes in one way: from the moment H3 sends `SIGUSR2` until `Promotion` has seen the promoted `server.json`, a candidate exit (75 or any other status, or a signal) is not raised there; `check()` leaves it to `Promotion`, whose `poll()` in the same turn reads `child_status(self.server)` and raises `handover.HandoverFailed('H3', <status>)`, which is W3. A candidate that exits before H3 (during the probe rounds) or after promotion completed raises in `check()` as today and is W2: it failed as a version. `check()` also reaps the old Bun if it exits on its own (`os.waitid(..., WNOHANG)`; see the known limits).

- **H1. Probe.** Rounds of `upgrade_health.check(STATE, candidate_pid, server_file='candidate.json')` every `INTERVAL` (2 s) until `DEADLINE` (120 s) from the first poll, as `Confirmation` does. `probes()` takes the console URL from `candidate.json` (the private address) and requires `pid` equal to the candidate's; the console probe passes only with status 200 and `x-sbarbase-pid` equal to the candidate's pid (`fetch` returns the header for that probe). Every gateway probe goes to the private address, so no probe can reach the old Bun.
- **H2. Recheck the old group.** The old Bun's current `listeners-<pid>.json` must say `frozen: true` (A7: its Studio and Functions Storage timers open and close no fixed listener any more, so the set H4 to H8 see cannot change on the old side; the candidate binds everything at H3 from sources B9 has already settled). Then as Q7 against that record; each listener's inode is recorded as `inode_old`. A failure is W3.
- **H3. Promote and steer.** `os.kill(candidate, SIGUSR2)`, once. The candidate computes its fixed listeners from the same sources as any start (the console port, `databaseListen()`, `externalListen()` with the TLS material that `ensureDatabaseTls` keeps under `.secrets/upstream/database-tls` (the old Bun serves with the copy it loaded; a renewal by the candidate's start reaches only the candidate), the Studio state, the published endpoints) and, for each one: binds it (`serveLocal` fronts on `Bun.listen`, the database proxy and the external listener on `node:net`, all with `reusePort`); finds its own descriptor for it (the inode of the `0A` entry in `/proc/net/tcp` or `tcp6` with that local address and port that is also a `socket:[inode]` link in `/proc/self/fd`; exactly one must match); and attaches the program with `bun:ffi` `setsockopt(fd, SOL_SOCKET, SO_ATTACH_REUSEPORT_CBPF, ...)`. The attach takes effect at once for the whole group (measured: 40 of 40 new connections to index 1 right after the `setsockopt`). The candidate is index 1 when it joined directly after the old socket, which H2 proved was alone; if a same-user socket joined between H2 and H3, that socket is index 1 and gets every new connection on that port from the attach until H4 counts three members and W3 ends both Bun processes (known limit). Only when every listener is bound and steered does it write `listeners-<pid>.json` (`role: candidate`, the full list, `steered: true` on each) and then `server.json` `{url: <shared>, pid, protocol, private: <private url>, promoted: true}`, and start its Studio and Functions listener timers and its own TLS renewal check (`watchDatabaseTls`; the old Bun stops its check when it drains) (a listener they open later is not shared and not steered). The Studio internal and Functions Storage binds at H3 are one strict attempt, not the timers' log-and-retry steps (which only log a failed bind and return normally): the implementer calls the same bind code with failure raised, and a failed bind, or `runtimes()` returning fewer environments than the wanted set, is a failure too. If any bind, descriptor match or `setsockopt` fails it stops every fixed listener it bound, writes nothing and exits 75, before the record is written: a fixed listener never fails silently at promotion. Studio and Functions Storage listeners that the timers open after promotion keep R7's behaviour: a failed bind is logged and tried again every 2 s; the database listener stays fail closed as R7 makes it. The supervisor waits up to `PROMOTE_SECONDS` for that `server.json`; a timeout or an exited candidate is W3.
- **H4. Check the groups.** For every listener in both records: exactly two listening sockets on that address and port, one of them `inode_old` (still a descriptor of the old Bun), the other an inode that is a descriptor of the candidate. `inode_old` was in the group (H2) before the candidate created any socket for it, so the join order is old at index 0, candidate at index 1: the kernel appends a joining socket to the group's array and moves the last one into a gap only on removal. A listener only the candidate has: exactly one socket, the candidate's; no steering needed. A listener only the old Bun has is logged and closes with it only when the candidate's wanted set lacks it (the new version chose not to open it); a listener the candidate wanted and could not bind already ended at H3 with exit 75, so an old-only listener that is in the candidate's wanted set is W3. Any other count or owner, including a third member of the same user, is W3.
- **H5. Check the steering.** The candidate's record must say `steered: true` for every listener it shares with the old Bun (H3); the supervisor attaches nothing and holds no socket. The program the candidate attached applies to the whole group; it sends every new connection to index 1, which H4 proved is the candidate. A listener whose order H4 did not prove would send new connections to the old Bun; H4 stops that case before H8 (W3). From here every new connection on every shared port goes to the candidate; the old Bun accepts only what was already queued on it.
- **H6. Recheck.** H4 again: the same two inodes per port with the same owners. A change (a listener rebound in between) is W3.
- **H7. Verify.** `VERIFY_CONNECTIONS` new connections to `127.0.0.1:<console port>`, each `GET /health`, in a background thread, each with `VERIFY_TIMEOUT`: every answer must be 200 with `x-sbarbase-pid` equal to the candidate's. One answer from the old pid, or none, is W3. The other fixed listeners do not speak HTTP; H4 to H6 are their proof.
- **H8. Retire.** `os.kill(old, SIGTERM)`: R7's graceful stop. At the signal every answer starts carrying `connection: close` and Realtime sockets are closed; for `ACCEPT_GRACE_MS` it keeps accepting, which empties its queue (steering sends it nothing new; the database proxy and the external database listener forward a session they accept in that grace); after `settled()` (at most `SETTLE_MS_MAX`) it closes its listeners and its quiet kept-alive connections and drains in-flight requests and database sessions up to `SBARBASE_DRAIN_MS`. Once its sockets leave the groups the candidate is the only member, and with one member the program's `1` is out of range and the kernel uses its hash; the program still steers any socket that joins later to index 1, so it is detached at H9a. The hold (scope `management` since B9a) stays in force the whole time, so the old Bun accepts no control change while it drains (Hold: one writer).
- **H9. Wait.** Each turn `os.waitid(P_PID, old, WEXITED | WNOHANG)`. At `RETIRE_WAIT_SECONDS` after H8 without an exit: `os.killpg(old, SIGKILL)` and `os.waitid(P_PID, old, WEXITED)` (immediate after `SIGKILL`); its remaining connections are cut, as today's stop cuts all of them. Once reaped: `handover.json` and the old `listeners-<pid>.json` removed, `retiringPid` dropped from `supervisor.json`. Then H9a.
- **H9a. Release the steering.** `os.kill(candidate, SIGUSR2)` a second time: the promoted Bun calls `setsockopt(fd, SOL_SOCKET, SO_DETACH_REUSEPORT_BPF (68), &zero, 4)` with `zero` a 4-byte `int` 0 (the kernel refuses an option length below `sizeof(int)` with `EINVAL` before it reads the option: measured, `detach_null.py`, the reviewer's, rerun: `NULL, 0` gives `EINVAL`, the `int` form returns 0 and a second detach gives `ENOENT`) on every listener it steered and rewrites its record with `steered: false`. A program left on a group is not harmless: measured (`leftover.py`, the reviewer's, rerun 3 times), after the old member closed, a later same-user socket that joined the group got 40 of 40 new connections; after the detach, new connections split by the hash again (16 and 24, 14 and 26, 21 and 19; the reviewer measured 17 and 23, 22 and 18, 19 and 21). A detach that fails is logged and changes nothing else: the handover is complete. The supervisor checks the record at its next turns and logs if it still says `steered`.
- **H10. Confirm.** Only now `upgrade_confirmed(catalog)`: it saves `confirmed` and releases the hold. If the save fails, the next round (H1's form: `candidate.json`, the private address, the pid check) runs after `INTERVAL` and confirmation is tried again. The old Bun is already reaped, so no answer can come from it. From the round that passed at H1, H3 to H10 must finish within `HANDOVER_SECONDS`; past it, W2.
- **H11.** Confirmed: `self.confirm = None`, the worker starts, `publish_current()`, as today.

## Hold, snapshot and who may write

**Order (B8, B9a).** The full hold, then `HOLD_SETTLE_SECONDS` (on a monotonic cache, R7 item 5), then the snapshot; the hold narrows to `management` only once the runtime start has returned (B9a). Writes the old Bun accepted before the marker took effect are in the snapshot; writes after it are refused. Before B8 the old Bun serves without any hold, exactly as the old supervisor's Bun does today until it is stopped, and those writes are in the snapshot too.

**Scope.** The marker's `scope: management` is R7's: an allowlist of the tenant data plane (each environment's gateway routes, `DATA_PLANE` in `src/gateway/hold.ts`, its Realtime sockets, direct database access and the Functions' Storage) flows; everything else is held, `/v1` and `/mcp` included (503), management changes get 409 except what `passesHold` lets through today; a marker without a scope, unreadable, or with a scope the reader does not know is the full hold. Both processes read the same marker, so the candidate on its private port and after promotion is held the same way. Files outside the stores that both processes read (`endpoints.json`, `database.json`, `studio.json`, write pauses, the runtime secret) are rewritten by the new version from B9 while the old Bun still routes with them; `PROTOCOL` versions their format (Names), so an equal protocol means the old Bun reads what the new code writes.

**One writer of control state.** From B8 until H10 both Bun processes refuse every control change the way back would lose; the hold is released only at H10, after the old Bun has been reaped at H9. There is no moment where two versions both accept control changes. What both may still write on the paths that keep flowing, with the reason each is accepted:

| Write | Store | Path | Why it is accepted |
|---|---|---|---|
| `catalog.environmentSaturated` (an operator notice in the outbox) | control catalog | the gateway's pressure monitor (`lab/upstream-app.ts`), on data plane traffic | refreshed by the next saturated minute; holding it would hold application traffic |
| `catalog.touchStudio` (Studio activity) | control catalog | a Studio host on the console port, which no hold covers today either | the next Studio request writes it again |
| the management Auth realm's sign-in, refresh and sign-out; "roll back", "check now", update settings | management Auth, `.lab/upgrades` | `passesHold`, as under today's hold | the way back does not restore them, so nothing is lost |

`access_tokens.last_used_at` is written only through `/v1` and `/mcp`, which the scope holds. A way back after promotion loses only the first two rows above, written between the snapshot and the way back, which today's way back cannot lose because no Bun runs then. Both processes open the stores with `journal_mode=DELETE` and a busy timeout; Q4 guarantees the same schema in both.

## Ways out

**W1. Ending the old Bun before any restore.** No snapshot is ever restored while a Bun process or any other child of this start has a store open (`upgrade_guard.restore_snapshot`: "Callers make sure nothing has the stores open"). The exact places in `lab/dev.py`:

1. `Supervisor.run`'s `finally`: `self.retiring.end(also=self.server)` takes the place of `terminate_group(self.server)`, after the scheduler, update, backup, Studio, sign-in, Data API and toggle children; the worker follows as today. Both Bun processes get `SIGTERM` at the same moment and share one `END_GRACE_SECONDS`, so with `SBARBASE_DRAIN_MS` at its cap (19 s) a stop needs about 20 s for both, 20 s for the worker and up to 90 s (`STOP_STAGE_SECONDS`) for the runtime stop: about 130 s against `TimeoutStopSec=150`, the same as today's budget plus nothing for the second Bun. So whenever `run` returns or raises, both Bun processes and every child it started are reaped.
2. `main`'s `except BaseException` branch: after `failed = True` and the message, and **before** `upgrade_outcome(False, reason=detail)`: `retiring.end()`. It covers every failure raised before `Supervisor` exists (B8, the settle stage, the console build, the runtime start). Stages started with `run_stage` are reaped in its own `finally` before the exception arrives here. Order: candidate and children (1), old Bun (2), then `upgrade_outcome(False)` restores, then `SystemExit(1)`.
3. `main`'s `finally`: `retiring.end()` before `close_runtime`, so a stop never stops the runtime under a serving Bun.
4. The module level `finally` (B3) for exits before `main`'s `try`.
5. W3 and W5 end both processes the same way before they leave the runtime and exit; neither restores anything.

**W2. The way back.** A failure of the new version (B8, B9, H1 deadline, a candidate that exits, H10 past its deadline): W1 then today's `upgrade_outcome(False)` (`after_start(False)`, `rollback(automatic=True)`, `go_back`, `complete_way_back`: checkout back, then the snapshot restored when `attempted_at` is set) and exit 1. The service manager starts the previous version through its full path, the kept runtime record having been discarded (`close_runtime` with `keep` false stops the owned runtime). A failed handover costs what a failed upgrade costs today.

**W3. A handover failure of a version that passed its round** (H2 to H7, a bind failure or timeout at H3): the version is not at fault, so there is no way back. `Promotion.poll` raises `handover.HandoverFailed(step, reason)`; `Supervisor.run` ends both Bun processes in one grace (W1, 1); `main` catches `HandoverFailed` before `except BaseException`, writes `handover-failed.json` with this `to` (Q11), and takes W5. Nothing was signalled to the old Bun yet. The next start is today's planned restart of the same version, gated as today, and the next move to this commit never tries the handover again.

**W5. Today's planned restart of the same version.** Used by W3, by a refusal at B4 or B7, and never after a failure of the version. Both Bun processes are ended (W1); `upgrade.withdraw_attempt()` closes the attempt the guard opened and takes it back out of its count (under the upgrade lock: `guard.open` false and `attempts` one less, never below 0), because the version reached no verdict and the restart that follows counts its own; the hold marker and the snapshot stay for that start (`before_start` keeps the snapshot once `attempted_at` is set, and writes the marker again); when no stop was asked (`asked` not set), `close_runtime(..., keep=True)` leaves the runtime through `leave_runtime(origin)` (origin is `HEAD`, the version starting next), so phase 1 adopts the containers, and the process exits 42. When a stop was asked at any point (for example during the grace that ends both Bun processes), `keep` is false, as today's `keep = restart and keep_runtime and not asked.is_set()`, and W5 ends as W4: attempt closed, runtime stopped, exit 0, and the record of the failed handover stays. If `leave_runtime` declines, the runtime is stopped after both Bun processes are gone, as in A3. A refusal at B4 comes before `main`: the runtime is untouched and the record A3 wrote, not yet claimed, stays for the next start; B3 ends the old Bun and the process exits 42 (with a stop asked, it exits 0 and the record ages out as for any stop in that window, `kept_runtime.MAX_AGE`).

**W4. A stop** (`systemctl stop` or `restart`, `docker stop` or `restart`, Ctrl+C): the handler sets `asked` and `stop_event`; the loop ends, or the next `run_stage` raises `InterruptedError` if the stop came before the loop (B1 delivers a stop that was pending across the exec, so this can happen as early as B4); W1 (1) and (3) end both Bun processes; `main`'s `finally` calls `upgrade_close_attempt()` whenever `(gated or attempt_open) and not failed`, so a stop before B8 (where `gated` becomes true) still closes the attempt B5 opened and the next start's guard does not take it for a crash; `close_runtime` stops the runtime; exit 0. A restart then starts fresh: no exec marker, so B2 removes the stale record, and the gated start of the same version runs through today's path. In the old supervisor a stop cancels the exec (A3, A6).

## Residual races and known limits

- **Idle keep-alive close.** An idle connection the old Bun closes at the end of the H8 grace (about 0.3 to 1.3 s after the signal) can be the one the TLS proxy's `fetch` picks for a request at that instant. Numbers from the code: the console's inner HTTP server closes an idle connection after `keepAliveTimeout` 5000 ms (`src/http/local-server.ts` `serveLocal`), with `headersTimeout` 10000 ms and `requestTimeout` 30000 ms (150000 ms for the Functions' Storage); the TLS proxy bounds a client request idle at 10 s (`deploy/console-tls-proxy.ts`) and sets no idle limit on its upstream pool, and Bun's `fetch` kept an idle pooled connection open for 90 s (`keepalive/idle.ts`), so the server side always closes first. Measured with a server closing an idle connection while the client reuses it: GET 0 of 2000 lost (Bun's `fetch` sends a GET again), POST 728 of 2000 `ECONNRESET` (`keepalive/race.ts`); with `connection: close` before the close, 0 of 2000 for both. So: connections busy at or after the signal close cleanly (R7's `connection: close`), and the residual is a non-idempotent request sent on a connection that stayed idle through the H8 grace, in the moment between the old Bun's close and the proxy seeing it. The proxy answers it 502 (it retries only refused connects). Measured on R7's stop with 200 kept-alive clients pausing up to 600 ms between requests: 2 and then 4 of about 20,600 and 20,900 requests over two series of 10 stops got no answer; clients sending back to back lost none. The same race already happens today on every connection at the 5 s idle close; the handover adds at most one occurrence per connection pooled to the old Bun. Known limit; closing it needs the proxy to retry, which is the proxy's own release.
- **Old Bun crashes before promotion** (deferred, spec D13). Nothing listens on the fixed ports until H3; the window is bounded by `DEADLINE` and is never longer than today's restart.
- **The console build is swapped under the old Bun** (deferred, spec D14). B9 adopts the staged build into `.lab/ui` while the old Bun serves it (`lab/ui-static.ts`); an operator loading the console in that window can get the new page against the old management API or an index whose hashed assets are gone. Operator console only; no application traffic or control state.
- **A management request still running `HOLD_SETTLE_SECONDS` after the marker.** It started before the hold took effect and commits after the snapshot; a way back loses it. Handlers are short; recorded, not held.
- **No supervisor lock from A4 to B6.** The locks are released before `execve` and taken again by the new program (the guard needs to take them itself). A terminal start in that gap refuses on the live record (B2); a command that takes `supervisor.lock` directly in that second, such as `lab/upgrade.py rollback`, can run, and finds the upgrade not yet attempted, so it restores no snapshot.
- **Tenants get 503 from B8 to B9a.** The runtime start may stop or replace containers, so the full hold covers it. With `SBARBASE_ROLLING_SERVICES` naming `rest` and a release that changes no computed setting, `up` may touch nothing, but this design has no proof of that before it runs, so it does not narrow earlier.
- **Repository conventions (deferred, standards round 2 D10).** This note is not yet indexed in `docs/engineering/README.md`, and the experiments are cited by paths outside the repository; both belong to the docs checkpoint, and the Tests section already requires the experiments to become repository tests.
- **`management.json` content** (deferred by the reviewer, kept here). `lab/upstream-app.ts` `openUpstreamApplication` reads the file once (`load`) and passes `management.auth` as a string to `application(...)` (about line 108) and to `invitationAccounts(...)` (about line 110). From `PROTOCOL` 1 both take a getter, `()=>(readJsonCached('.lab/upstream/management.json') as {auth:string}).auth`, called on each use, with the Bun test above. Even so, if B9 replaces the management Auth container (a computed setting changed), operator sign-in through the old Bun fails between the replacement and the rewrite of the file. Operator console only; tenants are under the full hold then.
- **A stray same-user socket in a steered group.** From H3 until the detach at H9a, a socket of the same user that joins a fixed port with `SO_REUSEPORT` (an operator running `bun lab/upstream-server.ts` by hand, a live check) can be index 1 and receive every new connection on that port. Between H3 and H8 H4 and H6 see the third member and W3 ends the handover; between H8 and H9a nothing checks, and it lasts at most `RETIRE_WAIT_SECONDS`. Without steering such a socket would receive a hash share, which is wrong too; the steering makes it all.
- **Partial promotion.** Connections the kernel queued on the candidate's listeners between its first bind and a failing one are reset when it exits 75.
- **Tenant requests reach the unconfirmed version** from H5 to H10 (at most `RETIRE_WAIT_SECONDS` plus one round). It passed a full health round first, and the data plane writes the environment databases, which no way back restores today either.
- **Per-process state doubles** for the drain window: admission, pressure and request logs (`RequestLog` is in memory; the old process's recent requests are lost, as on any restart).
- **Studio sessions** are stopped by `reset_studios` at B11 while the old Bun still proxies them, as on today's start; they start again after confirmation.
- **Readiness reporting.** `install_server.py wait-console` reads `server.json` against `supervisor.json`'s `serverPid`: from A2 to H3 they disagree and it reports not ready, as it does during today's restart.
- **External database guard state.** The external listener's per-address limits and sign-in lockouts (`ExternalGuard`, `src/http/database-external.ts`) live in the process's memory, so the candidate starts with none: an address locked out on the old Bun can try again from H3 on. The same happens today at every restart. Known limit.
- **Only IPv4 and IPv6 TCP listeners of the same user** are steered; the database proxy is IPv4 (`host-preflight.sh` requires an IPv4 database bind), and the external database listener is IPv4 by default (`127.0.0.1`) but may be bound to `::` or `::1` (`SBARBASE_DATABASE_EXTERNAL_BIND`), in which case H3 finds it in `/proc/net/tcp6`. A listener that is not in a Bun process's record is not handed over.
- Everything above is a design. Nothing is measured end to end, through the TLS proxy, with real environments.

**Compatibility rule.** A writer checks only what it writes: the keys it sets, their types, and that the value it patches is an object. It preserves every other key, in the file and inside the entry it patches, whoever wrote it. It never rejects a key it does not know. Both ways:

- A new key is optional by default. Older readers ignore it, older writers carry it through untouched, and its own readers treat it as absent when an older version wrote the entry. Adding one appends to the optional part of `handover-formats.json`, changes no hash and needs no protocol bump. Optional keys are append only: once a release declares one, its type, its being optional and its meaning stay as they are while the protocol is the same (Q3 and (2)); changing them needs a new `PROTOCOL`.
- A key whose absence an older reader would take as "allowed" (a new restriction, a flag that turns something off) must be declared required, never optional: the old Bun, which does not know it, would otherwise serve what the new version restricts. Declaring it required changes the hash and so needs a new `PROTOCOL`, and no overlap happens.
- A new required key (one the new version's readers cannot do without), a removed or renamed key, a changed type or a changed meaning changes the hash and needs a new `PROTOCOL`. Q3 then refuses the handover, so the old Bun never reads such a file; the upgrade takes today's restart path, which works because nothing of the old version runs once the new one writes. A release with a new required key also writes it for every entry its readers use in its own runtime start, before its Bun starts.
- The way back: P1 patching a file P2 wrote succeeds, because P1 checks only its own keys and carries P2's through (a test does exactly this with fixtures from the next shape). P2's keys stay in place for P2's next try, and P1's readers ignore them.

The writers apply whether the switch is on or off. Under this rule they write what today's code writes, byte for byte apart from key order, and refuse only a malformed value of their own keys, which today's code never produces (piece 4 runs every writer on the current fixtures). That is what keeps "off is today's behaviour" true.

## As built

Built in `lab/handover.py`, `src/http/handover.ts`, `lab/dev.py`, `lab/upstream-server.ts`, `lab/upgrade.py`, `lab/upgrade_health.py` and `lab/runtime_files.py`. The sequence, the records and the failure table are as designed. Where the build differs, and why:

1. **H2 waits for the freeze.** The old process rewrites its listener record with `frozen` at the next tick of its 2 s timers after `handover.json` names it, so an immediate check could fail a healthy handover. H2 gives it `FREEZE_WAIT_SECONDS` (5) before it is W3.
2. **`Promotion` takes more arguments.** `Promotion(supervisor, retiring, confirmed, ...)`: the confirmation is a callable from `lab/dev.py`, which the module cannot import. `promote_seconds` and `handover_seconds` default to `PROMOTE_SECONDS` and `HANDOVER_SECONDS` and exist so a test on a starved host can stretch them.
3. **`DECLARED` is read at module load.** By the time Q3 compares, the checkout holds the target, so the file there is the target's. Q3 compares the target's declaration with the one this version read when it started.
4. **Q4 uses the running version's code.** `release_channel` and `console_build_check` are imported at the top of `lab/handover.py`, so the move is judged by the code that is running, not by the moved checkout's.
5. **H9a also rewrites the role.** After the release the promoted process sets `role` to `serving` in its listener record and freezes again when named, otherwise it could not be the old process of the next handover (Q6 requires `serving`). Until the release it stays `candidate`, which H4 to H6 read.
6. **`retiring` is cleared after confirmation.** `Supervisor.retiring` is `None` once the handover is confirmed, otherwise a later stop or handover would end the serving process through `Retiring.end(also=...)`.
7. **The plan's console process stops before the way back.** In the old supervisor `retiring` is inert, so `main` stops the process that was to survive the exec (`stop_kept_console`) before `upgrade_outcome(False)` restores a snapshot, on every failure path.
8. **`localhost` is recorded as `127.0.0.1`.** A database bind of `localhost` is matched in `/proc/net/tcp` as 127.0.0.1; if the process bound `::1` the descriptor match fails and the candidate exits 75 (W3).

9. **B2 also runs for an unmarked start.** `dev.ordinary_start()` calls `handover.adopt(None, False, ...)` before admission, the guard and any lock: it removes a stale `handover.json` and refuses when the record names a live process that is not this one's child. The console process freezes only when the record names its pid and its start time (`namedForHandover`), so a stale record cannot freeze a later process that has the same pid.
10. **`handover-failed.json` is written for steps H2 to H7 only.** A refusal at a start gate (B4, B7), the no-pending case (B8) or a stale console build (B9) is W5 without the record, so a transient condition never rules a commit out for good.
11. **B8.** A handover start whose `upgrade_prepare` finds nothing pending raises `HandoverFailed('B8')` before the supervisor is built: no candidate is started beside the old process, and today's restart of the same version follows.
12. **A step never signals a reaped id.** `Promotion.step_verify` skips the SIGTERM to the old process when `Supervisor.check` already reaped it (B13).
13. **The checked writers judge only what they write.** `write_endpoints` checks the entries that differ from what the file has and `update_endpoints` checks the entry it patches, so an entry a later shape wrote cannot stop another environment's address from being published; `write_database` and `update_management` write over an unreadable current document, as the code they replaced did. `update_endpoints` is used by `rolling.point` and `write_pause.start_functions`.
14. **`serviceConcurrency` is declared** as an optional key of an `endpoints.json` entry, together with the `url` and `tenantHost` parts of `storage`, `functions` and `realtime` that the routing path reads; `FORMATS[1]` is unchanged because the hash covers required keys only.
15. **Direct path readers.** These callers hold a path and not a document and use the public accessors of `lab/runtime_files.py`, each for the reason `PATHS` in `lab/test_handover_formats.py` gives: `install_server.py`, `durable_runtime.py`, `database_move.py` (the secret's path to git or another program), `host_watch.py` and `studio.py` (a path that tests replace), `lifecycle_auth_realm.py` (`private_json` checks mode and owner) and `write_pause.py` (`folder` and `record_path`). The scan fails if another file starts using an accessor.
16. **Steering trial.** `steering_works` finds its port without `SO_REUSEPORT` (so it never joins another process's group), waits up to `STEERING_WAIT_SECONDS` (10) for a stalled loopback connect, and is tried twice; a kernel that ignores the program fails both.

17. **Python reads `localhost` as 127.0.0.1**, as the Bun side does (item 8), and any other host that is not an IP address is a `Refused` in every check, so H2 and H4 take W3 and not the way back.
18. **The health probes read the console's files as they always did** (checked by a test against the old reader): a missing `management.json` or `endpoints.json` skips its probes, a malformed one fails the round as "health probes unavailable".

Known limits of the build: (a) a new connection can wait for the promotion window, about 0.5 to 1 s on a quiet host and up to 1.5 s under load, because the candidate's promote section is synchronous; seconds-long loopback SYN stalls were seen under back-to-back client load on a host with tens of thousands of TIME-WAIT sockets, also with no handover in the control. The live gate (cp9) measures the real gap; the 4 ms pacing of the test clients is the honest fix for the tests, not a cure. (b) The port-claim fixture (`tests/fixtures/ports.ts` and its Python twin) can see a rename onto an empty directory succeed while a releasing run's recursive removal is in progress; that is test infrastructure only.

Test notes: the process test runs the steering once with 8 looping clients (the 150 runs under 24 busy loops are the bar that repeats it), and `tests/fixtures/handover-process.ts` re-implements the gateway and signal wiring of `lab/upstream-server.ts` over a stand-in application; the real entry point is covered by `tests/handover-server.test.ts`, with the database listeners off. Known and deferred: `application.ts` validates the management Auth address once at construction (a rewritten `management.json` is not re-validated per use); the first H10 retry round is not pinned to `INTERVAL`; the durability of `handover.json` is pinned by a spy only (a torn record only falls back to today's restart).

Other build notes: the admission credit is read by `kept_runtime.admission_credit_mib()` in the four admissions, so none of them imports `lab/handover.py`; `lab/runtime_files.py` holds the paths, reads and checked writes of the six files, and `lab/test_handover_formats.py` scans that nothing else names them. The keep-alive race is recorded in the note, not asserted by a test.
