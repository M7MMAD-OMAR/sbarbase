# Whole-cluster restore onto a chosen image

Design note for upstream currency P3 ([plan](plans/2026-10-14-upstream-currency.md), section 3). This note fixed the approach before the code; each part below is its own reviewed checkpoint. Parts 1 (`lab/database_volume.py`, `--to-volume`), 2 (`lab/cluster_inventory.py`), 3 (`lab/cluster_rebuild.py`) and 4 (`lab/cluster_takeover.py`) are built, unit tested only.

## What it is for

Two situations need the installation's database cluster rebuilt from backups, on an image the operator chooses, on the same host:

- The way back from the PostgreSQL step (A7, 17.6.1.166 to 17.11.0.004) when the newer image changed extension versions or catalogs, so the old image cannot run on the volume.
- A database move (`lab/upgrade.py database`, P1) that removed the old container and whose new image never becomes ready: every exit refuses until this exists ([upgrades guide](../guides/upgrades.md#moving-to-another-postgresql-image)).

Out of scope: moving to another host. That needs the credentials and the control state carried across, which is the fresh-host recovery work (`lab/installation_recovery.py`), not P3.

## Approach

The export is the supported backup run, not a new format. `lab/backup.py create all` already writes, in one run, every environment database (`pg_dump -Fc` inside one snapshot), `storage_metadata`, the management database and an installation manifest that records every image pin, each with sizes and SHA-256 digests. What a run lacked for a fresh cluster was the cluster level, the roles; part 2 adds it. P3 does not export role passwords: on the same host the runtime creates every scoped login from its own stored values (`lab/durable_runtime.py` `provision_database`, `storage_control`, `management_auth`, the Realtime and direct logins), so a fresh cluster can be given the same logins with the same passwords. The rebuild (part 3) does not call those functions: it recreates each role from the run's recorded inventory with its own statements and takes only the passwords from the runtime's stored values. What the run must record is which roles exist and their attributes, so the rebuild can recreate them and prove the rebuilt cluster matches.

The rebuilt cluster lives on a new volume. Retained volumes are never removed, and the runtime named the database volume as a constant (`sbarbase-durable-pgdata`), so the volume became state the runtime reads (part 1), and the generation migration learns to move onto another volume as well as another image. The old volume stays as the way back from the restore itself; after a stuck move it is not untouched, since the replacement that never became ready ran the newer image on it.

## Parts

Each is a checkpoint with unit tests and an independent review; none is accepted under the plan's section 10 until the rehearsal VM runs it.

1. **The database volume as state.** The runtime reads the database volume from a private record (absent: the current constant, so existing installations change nothing), checks a retained container against it, and refuses a record it cannot read. The generation migration intent can name a new volume (an intent version, like the image in P1), and the replacement is created on it; `create_replacement` and the adoption check (`replacement_identity`) require that volume. The runtime mounts only volumes it owns, so a rebuild creates its volume as `sbarbase-durable-pgdata-<12 hex>` with the runtime's owner label (part 3), and the move refuses any other, or one that holds no PostgreSQL data directory, before it touches the old container.
2. **The cluster inventory in each backup run.** The run records the roles the runtime manages, per environment kind (auth, rest, storage, studio, realtime, developer) and the cluster roles (`storage_control`, `management_auth`, `supabase_realtime_admin`), with their attributes, login state, connection limit, role-wide settings and the roles they are granted (with each grant's INHERIT, SET and ADMIN options, which the runtime relies on: Realtime gets the API roles WITH INHERIT FALSE), the parameter privileges granted to them (`GRANT SET ON PARAMETER log_min_messages`, cluster-level, which no dump carries), and the database image id the cluster ran. An allow-list rejects anything else, and attributes are checked per kind: REPLICATION only for Realtime, BYPASSRLS only where the runtime grants it. It is recorded in the run's installation manifest (`cluster`, from `lab/cluster_inventory.py`); a role that breaks its rule, or an inventory that could not be taken, is listed under `refusals` and the run still completes, so a wrong assumption here never stops backups, it only makes that run unusable for a rebuild. Roles the image creates are not listed (the image brings them back), and neither is a role someone created by hand. A run taken while Realtime migrates, when its login is briefly a superuser, records that as a refusal. Only role-wide settings are recorded: the PostgreSQL documentation for `pg_dump --create` says the archive carries the database's own access privileges and its `ALTER DATABASE ... SET` and `ALTER ROLE ... IN DATABASE ... SET` settings, and the restores here use `pg_restore --create` (`lab/restore_cutover.py`). That is taken from the documentation, not tested, and the rebuild does not check it: it compares each database's row counts and the role-wide inventory, not the database-level privileges or per-database role settings the archive replays.
3. **Rebuild into a fresh cluster** (`lab/cluster_rebuild.py <run> [--image-at COMMIT]`). From one backup run whose cluster inventory is usable and whose every backup verifies, and a chosen image (this checkout's distribution lock, or the lock of a named commit, proven on the local daemon and never pulled), with Sbarbase stopped (the supervisor, worker and backup locks held): a new volume `sbarbase-durable-pgdata-<12 hex>` owned by the runtime, and a build container `sbarbase-rebuild-<12 hex>` with its own owner `durable-rebuild` (nothing that settles or counts the runtime's containers acts on it), without network, started with the installation's database env file so the image's own roles get the same administrator password. The managed roles are created from the inventory with the passwords the runtime keeps (`runtime.json`, the developer login's own file); Studio's login, whose password exists only per session, and a developer login without its file are created closed and reported. Then management, `storage_metadata` and every environment are restored through the same archive planning a restore uses (`lab/restore_sql.py`), each under a stage name, checked against its backup's counts and renamed; the inventory taken again on the rebuilt cluster must match the recorded one, login state aside where it opens and closes. The build container is then removed (a removal that fails is recorded as `container_removed: false` and reported with the command to remove it) and the volume stays; a failed rebuild, an interrupted or stopped one included, also removes its container, keeps its volume and records the failure in `.lab/upstream/cluster-rebuild.json`; a version given to `--image-at` that cannot be read is refused before anything is created. No HBA authority is involved: the build container's files under `/etc/postgresql` vanish with it, and part 4's generation migration initializes the authority on the replacement. Unit tested only; nothing of it has run against a real daemon.
4. **Taking it into use** (`lab/cluster_takeover.py`). From the completed rebuild in `.lab/upstream/cluster-rebuild.json`, with Sbarbase stopped (the upgrade, supervisor, worker and backup locks held): the checkout's PostgreSQL lock must name the rebuilt image, and when it does not and a move is recorded, the checkout is moved back to the move's from version (the guard's verified move) only when that version's lock names the rebuilt image and its `lab/migrate-generation.py` knows `--supersede-stuck`. Then, by the migration record: none runs a generation migration onto the rebuilt volume and image; the stuck move's (retired container captured, archived and removed, replacement never captured) is superseded and finished from its archive ([container generation migration](CONTAINER-GENERATION-MIGRATION.md#superseding-a-stuck-migration)); one already onto the rebuilt volume is finished; any other refuses. Only once the runtime names the rebuilt volume is a begun move archived as `database-move-<to>-superseded.json` (its backups stay kept from pruning) and its record removed, so Sbarbase can start; a prepared move refuses until it is abandoned. Every step can be run again. The old volume is kept. Unit tested only; nothing of it has run against a real daemon.

## Limits

- Writes after the backup run are lost, which is why the A7 step and the move pause writes before the run (P5).
- Object files are not part of it: neither A7 nor the move touches the objects volume.
- Only the stuck state above is superseded. A move whose generation change keeps refusing while the old container still exists has no exit here yet.
- Unit tested only until the rehearsal VM runs it; the host does not have the memory for it yet.
