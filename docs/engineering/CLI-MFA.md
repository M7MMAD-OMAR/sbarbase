# CLI management MFA

This dependent CLI slice uses the existing public Supabase SDK pinned at `2.116.0` and original management Auth. It extends `lab/sbarbase.ts`; it does not change the accepted management MFA proxy, catalog policy or native runtime startup.

`relink`, `add-environment`, `rotate-key`, `studio` and `share` use the same login flow. Password sign-in establishes a session, then the SDK lists native factors and performs native TOTP challenge and verification. Protected management requests begin only after verification succeeds and the current native session reports `aal2`. There is no password-only fallback, copied token input, replacement TOTP validator or local authorization grant fabrication.

For an existing authenticator, enter its current six digit code at the hidden private terminal prompt. When several authenticators exist, choose a numbered sanitized label first. Passwords keep their existing inputs: hidden terminal prompt, `--password-stdin`, or the owner-only regular `0600` `--operator-file`. The authenticator code is always a hidden terminal input. It is never accepted from arguments, environment, standard input or a file. Piped password input can still work when the process has a controlling private terminal. A headless authenticated command refuses before login or management work. Local status, environment inventory and existing delegated tools keep their established authentication behavior.

For an account without verified factors, the SDK enrolls an original Auth TOTP factor. Its native setup key appears only on `/dev/tty` in an alternate terminal screen. Add that key to your authenticator app, then enter its current code without echo. The display is cleared after verification, an error, cancellation or a handled interruption. Enrollment keys and URIs are never sent to standard output, standard error, the CLI output hooks or a local file. Use a private terminal without recording: an external terminal recorder can capture any displayed setup key. Incomplete native factors are removed before a replacement enrollment, and a newly created incomplete factor is cleaned up on failure when Auth permits it. A failed cleanup does not authorize management access. Accounts with unsupported verified factor types are refused.

Hidden input captures the controlling terminal's original settings, checks that `stty` disables echo successfully, and restores those settings in `finally`. Failure to hide input refuses the prompt. Input uses the public Linux `/usr/bin/head` and `stty` utilities, with the controlling terminal supplied as a descriptor; credentials never become process arguments. Handled `SIGINT`, `SIGTERM` and `SIGHUP` stop the input child, clear the setup display and restore settings. Forced termination such as `SIGKILL` cannot run cleanup.

The SDK client keeps its session in private process memory with persistence, background refresh and URL session detection disabled. Auth transport is restricted to the selected console's management Auth prefix, refuses redirects and has a five second timeout. Protected API calls also refuse redirects and have a five second timeout. After every successful password login, all subsequent paths attempt native local sign-out, including failed MFA and failed management work. The accepted proxy policy revokes management grants in every session for any logout scope; ending a CLI session can therefore require an open console or another management client to verify MFA again.

Command cancellation handlers are installed before credentials are read. A handled interruption aborts in-flight Auth and management transport, prevents later protected work, and still permits sign-out with a fresh bounded signal. Setup-screen cleanup does not suppress command cancellation. If an interruption happens after an administrative request was already sent, inspect the installation before retrying; cancellation cannot undo an operation the server already completed.

`Deps.setupAuthenticator(secret, uri)` is an optional private display hook returning a cleanup closure. The real process writes the setup key directly to `/dev/tty`; injected native checks can keep it in memory to simulate an authenticator. The hook never grants authorization. `Deps.prompt(question, true)` supplies the hidden password or code input. Tests use synthetic secrets and record network requests in memory without printing them.

Focused verification runs under a systemd user unit with `MemoryMax=256M`, `CPUQuota=25%` and `RuntimeMaxSec=60`. Unit cases cover native SDK request sequencing, first enrollment, existing and multiple factors, rejected codes, `429`, unavailable Auth, an unexpected `aal1` verification response, headless refusal, hidden prompt cancellation, setup cleanup, sign-out and unchanged management command payloads. Unit transports establish CLI boundary behavior. Separate original Auth and real terminal evidence is required before claiming those paths work against a deployment.
