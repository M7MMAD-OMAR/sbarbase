# Roadmap from 2026-09-23

This replaces the "next step" paragraphs scattered across older checkpoints. It orders the work by what a user needs first, not by what is most interesting to harden.

## Who it is for, and the one promise

The first user is a developer or a small agency running Supabase applications for several clients on one server. They already feel the pain that self-hosted Supabase is one project per installation ([supabase discussion #4907](https://github.com/orgs/supabase/discussions/4907), open since January 2022, and the same answer in [#38048](https://github.com/orgs/supabase/discussions/38048) in 2025). Their other recurring complaints are backups, upgrades and an unprotected Studio ([#39820](https://github.com/orgs/supabase/discussions/39820)).

Other projects already share one PostgreSQL engine across projects ([GustavoMartins123/supabase-multitenant](https://github.com/GustavoMartins123/supabase-multitenant), [arunrajiah/supafleet](https://github.com/arunrajiah/supafleet)). Sharing is therefore not the differentiator. The promise is: **many Supabase projects on one server that you can back up, restore and upgrade without fear**, with credentials scoped to each environment. Every milestone below is judged against that promise.

## Done on 2026-09-23

- Documentation restructured into explain, guides, reference and decisions, with the engineering notebook kept intact; hand-drawn diagrams; a security policy and a threat model.
- An empty server simulated in a local VM (`lab/vm-rehearsal.sh`). It found defects the development host could not show, all fixed with tests:
  1. the acceptance checked the console before building it;
  2. block IO limits named a partition, which the kernel rejects, so the database never started on a normal VPS disk layout;
  3. the preflight asked for 8 cores and about 8.4 GiB free on every host; it now derives the figure from what the next start runs (4352 MiB and 2 cores on an empty server);
  4. every body-less POST gained an empty body over the real listener, so the console could not issue or revoke keys;
  5. the console port changed at every start, which would break an HTTPS proxy after a reboot (`SBARBASE_CONSOLE_PORT` now pins it);
  6. a failed first launch was reported as a retained source to adopt;
  7. the 1.7 GB database image pull hit a 600 second command timeout on a slower link, silently;
  8. the runtime refused to start below a fixed 6 GiB even after the preflight admitted the host; both now use one computation.
- `lab/first-project-check.ts`: the new operator's path end to end, including supabase-js through the gateway.

## Milestone 1: a real server (next month)

Buy per [choosing a server](../../guides/choosing-a-server.md). Then, in order:

1. Run `deploy/server-acceptance.sh --rehearse --install-unit --first-project` on the empty server. Commit the evidence under a server-specific name.
2. Pin the console port, put the TLS proxy in front with a public certificate, reboot, and confirm the console and an application both answer over HTTPS.
3. Seven-day soak with two real environments: memory, disk growth, log growth, restarts. Record it.
4. Measure, then lift or restate, the lab guard that allows at most four environments per installation (`lab/durable_runtime.py`, "Local runtime admission limit reached"). Memory, pressure and connection-budget admission already gate each new environment; the count guard predates them.
5. Turn on GitHub private vulnerability reporting so `SECURITY.md` works.

Acceptance: a stranger can follow [the quickstart](../../guides/quickstart.md) on the same kind of server and reach a working supabase-js call.

## Milestone 2: backups as a feature, not a procedure

Today recovery is a set of scripts, rehearsed on one machine, and exporting one environment stops the shared Storage process, which takes every environment offline.

1. Online per-environment backup: `pg_dump` of the environment database while it serves, plus a tenant-scoped copy of its objects under a Storage write fence for that tenant only. Other environments stay up.
2. An installation manifest (pins, routing, roles, configuration, secret references) backed up with each run.
3. Encrypted, off-host targets: an S3-compatible bucket or SSH/rsync. Retention by count and age.
4. A scheduled job driven by the supervisor, with operator notifications on failure (the notification channel already exists).
5. `restore` for one environment into a fresh database, verified before the route switches, keeping the pre-restore database until the operator confirms (the rename-then-drop pattern supabase-multitenant uses is a good reference).
6. A restore drill: the VM rehearsal restores last night's backup into a second VM and runs the first-project check against it.

Acceptance: a backup is taken while two environments serve traffic without a failed request, and it restores on another machine.

## Milestone 3: Studio per environment, behind login

Specified in [STUDIO-INTEGRATION.md](../STUDIO-INTEGRATION.md). Serve the pinned upstream Studio and postgres-meta per environment behind the console's authentication, never on the data plane's routes. Measure its footprint and make it start on demand if it is heavy. supabase-multitenant's OpenResty routing is worth reading before building; its shared service logins are not a model to follow.

Acceptance: two Studio tabs on two environments cannot see each other's data, and an unauthenticated request never reaches Studio.

## Milestone 4: upgrades you can undo

1. `pin_update.py` proposes a version bump; the preflight checks compatibility.
2. Backup before upgrade, automatically.
3. Upgrade one environment's Auth and REST first, run the first-project check, then the rest.
4. Rollback is supported until the first write after the upgrade; after that, forward repair only, stated plainly.

Acceptance: a VM rehearsal upgrades from the previous pins to the current ones and back, with data intact.

## Milestone 5: onboarding and daily operations

Invitations and roles in the console, an audit view, a small `sbarbase` command for the common tasks (status, backup now, add environment, rotate key), and install without a Git checkout (a release archive with Bun and the pins).

## Later

Realtime and Edge Functions per environment; capacity measurement on the real server to publish observed, dated figures; a second server and moving an environment between servers.

## Known debt, not scheduled above

- `/usr/bin/python3` 3.14 is required. Ubuntu 26.04 and Fedora 44 ship it; Ubuntu 24.04 (3.12) and Debian 13 (3.13) do not. The unit tests import under 3.12 except for a missing `cryptography` module, so lowering the floor looks feasible but needs a full run on those distributions.
- The acceptance records the unit as active in the same second it starts; it should wait for the console to answer.
- The service account is in the `docker` group, which is root-equivalent on the host. Stated in the threat model; a rootless or socket-proxy design is a later option.
- CI actions are pinned by tag, not by commit.
