## Required outcome

A completed project transfer preserves project, environment, database and application user identities and data, changes ownership to the destination organization, retires the transferred environments' previous platform credentials and grants, and proves replacement credentials work through the original pinned services. It does not report completion while a native rotation, consumer reconciliation, session retirement or resource inventory transition remains uncertain.

The source organization keeps ownership while an operation is pending. Transferred runtimes are paused and their previous runtime generations are retired before external effects. Pending operations remain observable after interruption. An authorized retry uses the same operation and the same reserved credentials. It never restores retired credentials or silently treats a partially completed transfer as a no-op.

## Planned operation and recovery states

1. Admission: verify both owners and MFA, destination uniqueness, exact environment and credential inventory, supported placements, no concurrent provisioning/lifecycle/service/configuration operation, no unhandled external vendor credentials and resource capacity. No credential effect occurs on refusal.
2. Intent: commit a project operation and per-runtime guards, capture source inventory and routing revisions, advance runtime epochs once, cancel only queued jobs whose original authority cannot survive the transfer, and pause runtime admission. Keep source ownership.
3. Private reservation: atomically write mode600 generated credentials with fsync and exact operation/inventory binding before use. Existing public intent with no reservation is recoverable. Existing reservation is reused. A mismatched or missing reservation after effects is a blocker.
4. Quiescence: drain selected gateway requests, close selected optional workers, fence every selected login and drain all selected database connections. Establish an original Storage tenant write barrier including already-authorized transfers. Reject unresolved prepared transactions and ambiguous writers. Preserve neighbors.
5. Native rotation: settle old Auth sessions first, then change native role passwords and signing material, selected Storage tenant database URL/JWT/JWKS, Realtime credentials and consumer configurations. Retire dormant saved credentials and old direct/Studio logins. Persist each pending effect before action and verify its postcondition before advancing.
6. Verification: original services accept replacements and reject the captured old credentials. Old grants, sockets and native client sessions are unusable. New same-tenant operations succeed, crossed-tenant attempts fail, and neighbor traffic and identities remain intact. Inspect actual role privileges and login state.
7. Inventory and ownership publication: append verified inventory generations and complete ownership atomically under the same operation, expected epochs, owner authority and native receipts. Record one ownership change event. Handle response loss by returning the settled operation.
8. Resume and settlement: reopen only the intended services under replacement credentials and settled ownership. Keep direct database access and Studio closed until destination obtains fresh credentials. An interrupted final resume is a distinct pending settlement, never a second credential generation. Remove private retired secret material only after a durable terminal receipt, leaving secret-free audit and reconciliation metadata.

Native effects are not a distributed transaction. They cannot be rolled back by restoring compromised credentials. A partial operation is fenced and resumable; it is not reported as a completed move. Native responses and journals must never expose generated passwords, JWTs, signed URLs, key contents or service environment inspection output.

Private publication uses a schema2 manifest durably written before the credential candidate. It binds exact candidate identity, operation binding digest, prior full-record digest and credential-free prior state, proposed revision/digest and reserved material digest. Candidate and directory durability precede rename; destination directory durability precedes marker retirement. Explicit `reconcile_publication(effect_started=..., expected_material_digest=...)` adopts only a uniquely proven legal generation and never generates credentials or native receipts. Initial revision0 reservation recovery may lack a public material digest only before all effects; every later recovery requires external continuity. Missing candidate with an exact previous target may persist an aborted-publication receipt and retain the prior native uncertainty. A bounded, deterministically ordered `publications` history replays legitimate repeated aborts after marker cleanup or response loss; `publication` remains present for one matching receipt. Duplicate copied manifests and unmatched current/future generation receipts remain blockers. Legacy markers, partial sole material, orphan/multiple candidates and mismatched binding, identity, revision or material remain retained and blocked. Plain content digests do not authenticate files against a privileged host adversary.

Filesystem recovery preserves historical verified receipts, which remain historical observations. Final native verification must recheck original services before ownership or resume. Successful file cleanup cannot turn a pending native effect into success. Source unit fault schedules prepare checks for candidate/marker write, fsync, rename and cleanup boundaries, but unexecuted tests and ordinary process-level faults do not prove all filesystem power-loss behavior.

## Source-only prerequisite result

Independent operational research found no tenant-wide writer barrier in original Storage v1.73.1, commit `a88e8eea60b69ee629f99f17b21cdb6578a2272a`. The native file backend does not honor its upload AbortSignal, and the uploader intentionally completes its metadata transaction with a fresh signal after bytes finish, even when the client disconnected. Native tenant configuration, deletion and queue APIs do not establish a selected-tenant active writer barrier. Therefore T5 remains an explicit architecture dependency, with no native or implementation acceptance claim.

A restricted shared-process profile would require durable, cross-process admission and native mutation settlement tracking for every mutating ingress. Lost acknowledgement, gateway crash, cancelled forwarding and untracked autonomous cleanup must leave transfer refused. Such a tracker is a proposed platform mechanism, not an original vendor API, and alone does not prove general interruption recovery. A separately owned original Storage process and volume per tenant supplies a native process boundary for future topology work; migration from a live shared process still needs its own admitted quiescence contract. Restarting the shared service or adding a filesystem lock that native writers do not honor does not satisfy neighbor isolation.
