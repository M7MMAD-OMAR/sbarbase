# Log In With Telegram for tenant projects

Status: researched and implemented in source on branch `feat/telegram-stars`, 2026-11-21. Labels: VERIFIED means read in the GoTrue source at tag v2.197.0 or run; INFERRED means reasoned, not run. Nothing here is deployed, and a real Telegram login needs a bot and its credentials, so it is not exercised. Not a production readiness claim.

## The question

A tenant project should be able to switch on "Log In With Telegram" from the console's Sign In settings, the way it switches on Google or GitHub, and its application then signs people in with `supabase.auth.signInWithOAuth({provider: 'custom:telegram'})`. Telegram is an OpenID Connect provider: issuer `https://oauth.telegram.org`, authorization `https://oauth.telegram.org/auth`, token `https://oauth.telegram.org/token`, keys `https://oauth.telegram.org/.well-known/jwks.json`, discovery `https://oauth.telegram.org/.well-known/openid-configuration`, response type `code`, PKCE `S256`, token client authentication `client_secret_basic`, ID token `RS256` by default, scopes `openid` and `profile` (and optionally `phone`), no email, no userinfo endpoint ([Telegram's guide](https://core.telegram.org/bots/telegram-login)).

## Research answers (VERIFIED from GoTrue v2.197.0, commit 4eee58f296d9698a1c2c0ae14d7a0b379c7622d3)

1. **Custom providers are not configured by environment variables.** Built-in providers read `GOTRUE_EXTERNAL_<NAME>_*`. A custom provider is a row of `auth.custom_oauth_providers` ([`internal/models/custom_oauth_provider.go`](https://github.com/supabase/auth/blob/v2.197.0/internal/models/custom_oauth_provider.go)), managed through the admin API. The only variables are `GOTRUE_CUSTOM_OAUTH_ENABLED` (default true), `GOTRUE_CUSTOM_OAUTH_MAX_PROVIDERS` (default 0, unlimited) and `GOTRUE_CUSTOM_OAUTH_EXTERNAL_URL` ([`internal/conf/configuration.go`](https://github.com/supabase/auth/blob/v2.197.0/internal/conf/configuration.go) line 87). The pin therefore needs no new variable; `GOTRUE_EXTERNAL_TELEGRAM_*` would be ignored.
2. **Admin endpoints** ([`internal/api/api.go`](https://github.com/supabase/auth/blob/v2.197.0/internal/api/api.go) line 430, handlers in [`custom_oauth_admin.go`](https://github.com/supabase/auth/blob/v2.197.0/internal/api/custom_oauth_admin.go)): `GET` and `POST /admin/custom-providers`, `GET`, `PUT` and `DELETE /admin/custom-providers/{identifier}`. They need an admin token (a JWT whose role is in `GOTRUE_JWT_ADMIN_ROLES`, here `service_role`), the same token Sbarbase already uses for `/admin/users` (`lab/durable_runtime.py` `token`). On Supabase self-hosting the `apikey` header carries the secret key; against the Auth container directly it is `Authorization: Bearer`.
3. **Payload** (`AdminCustomOAuthProviderParams`): `provider_type` (`oidc`), `identifier` (must start with `custom:`; the docs say 2 to 50 characters, lowercase letters, digits, hyphens and colons), `name`, `client_id`, `client_secret`, `scopes`, `pkce_enabled` (default true), `email_optional` (default false), `enabled` (default true), `acceptable_client_ids`, `attribute_mapping`, `custom_claims_allowlist`, `authorization_params`, and for OIDC `issuer`, optional `discovery_url`, `skip_nonce_check`. `openid` is added to the scopes when missing. An update takes only the fields that change; `provider_type` and `identifier` cannot change.
4. **Create fetches the discovery document from the Auth container.** `POST` calls `FetchAndValidateOIDCDiscovery` on `{issuer}/.well-known/openid-configuration` and refuses a different `issuer` value, and `ValidateOAuthURL` requires https and resolves the name to refuse loopback and private addresses ([`internal/utilities/url_validator.go`](https://github.com/supabase/auth/blob/v2.197.0/internal/utilities/url_validator.go)). The Auth container must therefore reach `oauth.telegram.org` at create time and at login time (the OIDC cache refetches the document; the token exchange and the key fetch follow). Telegram's document is live and complete: the endpoints above, `code_challenge_methods_supported` with `S256`, `id_token_signing_alg_values_supported` `RS256`, `ES256`, `EdDSA`, `ES256K`.
5. **`/authorize?provider=custom:telegram`.** `API.Provider` ([`external.go`](https://github.com/supabase/auth/blob/v2.197.0/internal/api/external.go) line 613) lower-cases the name and sends anything starting with `custom:` to `loadCustomProvider`, which looks the identifier up, refuses a disabled row and builds a `CustomOIDCProvider` from the discovery document. With `pkce_enabled` true GoTrue generates its own verifier and adds the S256 challenge to the redirect, whatever the client does about its own PKCE. The redirect URI is `API_EXTERNAL_URL/callback` (or `GOTRUE_CUSTOM_OAUTH_EXTERNAL_URL`), the same callback the console shows for every provider.
6. **Userinfo can be skipped, and is.** `CustomOIDCProvider.GetUserData` ([`internal/api/provider/custom_oauth.go`](https://github.com/supabase/auth/blob/v2.197.0/internal/api/provider/custom_oauth.go)) reads the `id_token` first, verifies it against the discovery document's keys, checks `aud` against `client_id` plus `acceptable_client_ids`, and returns. Userinfo is used only when there is no ID token. Telegram always returns one.
7. **Claims that reach `identity_data`.** The ID token is unmarshalled into `provider.Claims`, then `structs.Map` writes it to `identity_data` and `user_metadata`. Typed fields survive: `sub`, `iss`, `aud`, `iat`, `exp`, `name`, `preferred_username`, `picture`, `given_name`, `family_name`, `email`, `phone`. Two Telegram claims are not typed fields: **`id`** (the numeric Telegram user id, the value a bot needs to message or charge a user) and **`phone_number`**. They are dropped unless the provider lists them in `custom_claims_allowlist`; the listed keys then land in `identity_data.custom_claims`. `sub` is a separate opaque identifier (Telegram's example shows different values), and it is what GoTrue stores as the identity's `provider_id`. So Sbarbase sets `custom_claims_allowlist` to `["id"]`, and the Telegram user id is read from `identity_data.custom_claims.id` (in a database function, `auth.identities.identity_data -> 'custom_claims' ->> 'id'`).
8. **No email.** `createAccountFromExternalIdentity` needs an address unless the provider is `email_optional`. Telegram returns none, so the row must carry `email_optional: true`. The Supabase docs say the same.
9. **Nonce.** GoTrue's redirect flow never sends a nonce for a custom provider, and `skip_nonce_check` matters only for `signInWithIdToken`. Left false.
10. **Signing algorithm.** Keep BotFather's default `RS256`. go-oidc supports no `ES256K`, and Telegram withholds `profile` claims from `EdDSA` and `ES256K` tokens.
11. **Quota.** `MAX_PROVIDERS` 0 means unlimited; Supabase's cloud limit of 3 on the free plan is not a GoTrue rule.
12. **Version.** The Supabase docs name v2.196.0 as the first self-hosted release. The pin is v2.197.0, which contains the whole feature ([self-hosted custom providers](https://supabase.com/docs/guides/self-hosting/self-hosted-custom-oauth-providers), [custom providers](https://supabase.com/docs/guides/auth/custom-oauth-providers)).
13. **Secret at rest.** `SetClientSecret` stores the secret in plaintext unless `GOTRUE_SECURITY_DB_ENCRYPTION_*` is configured, which Sbarbase does not do. See the risks below.

## How Sbarbase applies Auth settings today (VERIFIED in this repository)

- The console saves a private file `.secrets/upstream/<runtime>-auth.json` ([`src/control/sign-in.ts`](../../../src/control/sign-in.ts), `PROVIDERS` at line 17) and records a pending revision. The supervisor runs `reconcile_auth` ([`lab/durable_runtime.py`](../../../lab/durable_runtime.py)), which recreates that environment's Auth with `auth_settings.configuration` (variables only), joins it to the outbound network when `egress_wanted` says so, waits for `/health`, and only then writes the applied copy. A failure puts the previous Auth back.
- Validation exists twice and must agree: `validate` in [`lab/auth_settings.py`](../../../lab/auth_settings.py) and `settingsFromInput` in `sign-in.ts` (`tests/settings-validation.test.ts` drives both).
- The registry [`src/control/auth-config-registry.json`](../../../src/control/auth-config-registry.json) lists each provider for the console's read side; `lab/test_auth_config_registry.py` checks that what it names reaches Auth under `GOTRUE_` names. [`lab/auth-names-check.py`](../../../lab/auth-names-check.py) is the live probe of those names. `ui/SignIn.tsx` holds the provider list with labels; `ui/ProviderIcon.tsx` the local icons; [`ui/assets/providers/SOURCES.md`](../../../ui/assets/providers/SOURCES.md) their licences.
- Egress: `egress_wanted` is already true when any provider is enabled, so an enabled Telegram entry joins Auth to the outbound network with no new rule. The outbound network is open to the internet; the default deny allow list is still the open item 8 of [the Authentication workspace plan](2026-10-30-auth-providers-workspace.md). This change does not weaken a default and does not close that item. A custom provider name can only reach what the Auth container can reach; GoTrue itself refuses non-https and private addresses at create time.
- The gateway forwards `/auth/v1/admin/...` with the service token to any caller holding the environment's secret key, so a tenant could already create `custom:*` rows by hand (INFERRED from `gatewayKeyAccess` and the Auth route table; not run).

## Design (smallest that fits)

Telegram becomes one more name in the provider list, with the same four inputs as the others (`enabled`, `client_id`, `secret`) and with rules that follow from its being fixed and custom:

- `client_id` is the bot id: digits only, up to 20.
- No `url` (the issuer is a constant), no `skip_nonce_check`. `email_optional` is always true: it is stored true whatever the input says, and the console hides the switch.
- `auth_settings.configuration` emits nothing for it (no `GOTRUE_EXTERNAL_TELEGRAM_*`).
- A pure function `custom_providers(settings)` returns the `custom:telegram` payload (`provider_type` `oidc`, issuer constant, scopes `["openid","profile"]`, `pkce_enabled` true, `email_optional` true, `custom_claims_allowlist` `["id"]`), or `None` when `telegram` is not in the settings.
- `durable_runtime.reconcile_auth` calls `apply_custom_providers` after the health wait and before the applied copy is written, against the container's own endpoint with the service token. It lists all custom providers (no type filter) and touches only `custom:telegram`: POST when absent; PUT when present and it is the fixed OIDC provider (without `issuer`, so no discovery fetch); DELETE then POST when a row of that name has another type or issuer, so the row always ends as the settings say; DELETE when the entry is saved disabled, or was in the last applied settings and is no longer named (the entry removed, or the whole settings file removed). An entry no settings ever named leaves a row of that name alone. A tenant's own other `custom:*` rows are never read for their secrets, changed or deleted. A failure raises, so the existing rollback runs, and `restore_custom_providers` first puts the row back: the secret of a present row cannot be read, so the prior row comes from the last applied settings (created again, or updated, with their client id and secret); a row the applied settings did not have and that did not exist before is deleted. The error names the HTTP status and the Auth error code, never a body.
- The registry entry carries `"mechanism": "custom_oidc"`; the read side and `changedKeys` name its keys `custom_provider:telegram.client_id` and so on, not as variables (there is none).
- The main settings file does not carry Telegram: `file_form` (Python) and `fileForm` (TypeScript) leave it out, and `load`, `load_applied`, `readSettings` merge the sibling file back in. Removing Telegram from the settings removes the sibling; removing the settings removes both applied copies.
- The admin calls use an opener with no proxy handler (`NO_PROXY` in `lab/durable_runtime.py`), so `HTTP_PROXY` and similar variables never see the service token or a client secret. Follow-up, not changed here: the two older call sites of `urllib.request.urlopen` in the same file (`http`, and the Realtime boot call) still honour those variables.
- `OWNED_PREFIXES` is unchanged: `GOTRUE_CUSTOM_OAUTH_*` stay the operator's own variables.

The console shows the callback URL it already shows for each provider; the owner pastes it into BotFather's Allowed URLs (Bot Settings, Login Widget) and copies the Client ID and Client Secret from there.

## Risks and limits, stated plainly

- **The secret is stored in plaintext in the environment's own database** (`auth.custom_oauth_providers.client_secret`), unlike the other providers, whose secret lives only in the Auth container's environment. The developer login is a member of the Auth login, so a tenant's own developer or service role can read it with SQL. The console still never reads it back. The rows live in the tenant's database, so a backup of that database contains the secret. Turning on GoTrue's database encryption would encrypt it but changes a global behaviour of Auth and is not done here.
- **Restore and rollback.** A restore of a backup made before Telegram was enabled has no row until the next save of the Sign In settings. Code older than this change refuses a settings file that names `telegram` (`providers`), which fails closed.
- **The row is rolled back with the container.** GoTrue reads `custom:*` from the database at request time, so the Auth that comes back after a failed apply would serve a changed row. A failure after the row was written puts it back from the last applied settings (see Design). That restore is best effort: if Auth refuses it, the refusal is written to the log and the original failure is still the one reported. A row that existed with no applied settings behind it (made by hand, then overwritten) cannot be restored, since its secret was never readable.
- **Reserved name.** `custom:telegram` belongs to this setting once a `telegram` entry is saved: a row a tenant made by hand under that name (OIDC or OAuth2, any issuer) is replaced by an enabled entry and deleted by a disabled one, and an entry that is removed later deletes the row too. A row under that name that no saved Telegram entry ever covered is left alone.
- **Egress** is open for every environment with any provider enabled; see above.
- **Phone.** `phone_number` is not a typed claim either. The `phone` scope is not requested; add it and `phone_number` to the allowlist together when it is wanted.
- **What is not verified.** A real login through Telegram, the token exchange with `client_secret_basic` and the ID token check against Telegram's keys. They need the owner's bot. The live probe checks everything up to the redirect.

## Functions and jobs (read-only research, VERIFIED in this repository)

- **`verify_jwt = false` for a webhook function.** A function is deployed with `verify_jwt` false in any of three ways: `verify_jwt = false` under `[functions.<name>]` in `supabase/config.toml` (read by `lab/functions-deploy.ts`), the field `verify_jwt` in `PUT /management/v1/environments/{id}/functions/{name}`, or `PATCH` on the same route with exactly `{"verify_jwt": false}`; the console's function Settings has the **Require a valid JWT** switch ([edge functions guide](../../guides/edge-functions.md), [EDGE-FUNCTIONS](../EDGE-FUNCTIONS.md)). A call with no key then runs the function and the caller's own headers reach it, so a Telegram webhook (`setWebhook` with a `secret_token`) can post to `<public url>/<runtime>/functions/v1/<name>` and the function must check Telegram's `X-Telegram-Bot-Api-Secret-Token` header itself, because anyone can reach it. With On demand Edge Functions a keyless call wakes the runtime only for a function with `verify_jwt` off, and the first call after a quiet period may answer `503` with `retry-after` while it starts; Telegram retries a webhook that fails. A function with `verify_jwt` off can be held busy by anyone who can reach the gateway (4 slots per environment, no per caller limit; EDGE-FUNCTIONS line 103).
- **pg_cron and pg_net.** The real extensions are refused on the shared server (`RESERVED_EXTENSIONS` in `lab/durable_runtime.py`; `create extension pg_cron` and `create extension pg_net` fail). An environment that turns **Scheduled jobs** on (Services page) gets `cron.schedule`, `cron.unschedule`, `cron.alter_job`, `cron.job`, `cron.job_run_details`, and `net.http_get`, `net.http_post`, `net.http_delete`, with the same signatures as pg_cron 1.6.4 and pg_net 0.20.4, in its own database ([scheduled jobs guide](../../guides/scheduled-jobs.md), [SCHEDULED-JOBS](../SCHEDULED-JOBS.md)). Requests leave only to http and https on ports 80 and 443, never to private, loopback or reserved addresses, and the one way back to the server is its public address. A call to `https://api.telegram.org/...` is allowed by that rule (INFERRED from the rule; not run). They need the developer role (direct database access turned on once). Not production ready; checked only in disposable containers.
