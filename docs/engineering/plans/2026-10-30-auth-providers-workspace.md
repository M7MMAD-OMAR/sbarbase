# Authentication workspace in the console

Status: study and proposal, 2026-10-30. Phase A0 (read side) is the first change after this plan. Labels: VERIFIED means read in code or run in this study; INFERRED means reasoned, not run. Not a production readiness claim. Evidence: [study.json](../../evidence/auth-config-study-2026-10-30/study.json).

## The question

The owner wants every Authentication setting of an environment (providers such as Google, Microsoft and GitHub, URL configuration, email templates, SMTP, sessions, MFA, attack protection, rate limits, hooks) changed from the UI like on Supabase's cloud, with no code or environment variable edits per project, and with the same experience. Everything is strictly per environment: a secret or setting of one environment is never readable, writable or inherited by another.

## Verdict

1. **Do not obtain the write UI from Studio.** The pinned Studio (2026.10.12, the same image `lab/studio.py` starts) has the Authentication pages in its bundle (providers, url-configuration, smtp, templates, sessions, rate-limits, protection, mfa, hooks, third-party), but with `IS_PLATFORM` false:
   - `useAuthConfigQuery` is `enabled: enabled && IS_PLATFORM && ref !== undefined`, so the page never requests `GET /platform/auth/{ref}/config` (VERIFIED in four client chunks). The write call is `PATCH /platform/auth/{ref}/config`.
   - The Studio server has no `/api/platform/auth/[ref]/config` route, only invite, magiclink, otp, recover, users and factors (VERIFIED from `routes-manifest.json`; `curl` answered 404).
   - Experiment (VERIFIED): one container of the pinned digest on loopback, no database; the built-in browser opened `/project/default/auth/providers`. It rendered skeleton rows under User Signups, the left menu listed only Users and Policies, and no request to `auth/config` was sent. A proxy that answers the call therefore changes nothing; forcing the flag on sends the whole app to the cloud sign in page, as the [Edge Functions study](2026-10-30-edge-functions-workspace.md) found. Patching minified chunks on every pin update is a fork in practice and breaks the rule that native Studio stays native ([STUDIO-INTEGRATION](../STUDIO-INTEGRATION.md)).
2. **Build an Authentication workspace in the Sbarbase console**, laid out like the cloud's: the same left menu, page names, field labels, descriptions, toggles, callback URL with a copy button, masked secret fields and one Save per form. Studio keeps Users and Policies, which work natively. Sign-in settings already exist in the console ([SignIn.tsx](../../../ui/SignIn.tsx), [sign-in.ts](../../../src/control/sign-in.ts), [auth_settings.py](../../../lab/auth_settings.py)): this plan generalizes them, it does not start over.
3. **Fidelity source.** The Studio bundle carries the cloud's own form definitions: titles, descriptions, field types and the key names of the platform config object (VERIFIED: 93 `EXTERNAL_*`, 34 `MAILER_*`, 24 `HOOK_*`, 21 `SMS_*`, 7 `RATE_LIMIT_*`, 7 `SMTP_*` keys, in the study evidence). The registry in A0 is built from them. An observation pass of the owner's real cloud project is still owed (gate G0): the Chrome this session reaches was not signed in, and signing in is not an agent action.

## What exists today (VERIFIED in code)

- One private file per environment, `.secrets/upstream/<runtime>-auth.json`, mode 0600, holds site URL, redirect allow list, signup, anonymous, three session lifetimes and 19 OAuth providers. A mail file `<runtime>-mail.json` holds SMTP and the email rate limits (`lab/mail_config.py`).
- `PUT /management/v1/environments/{id}/sign-in` validates, writes the file, and records a pending revision in the catalog (`auth_settings` table, audit event `sign_in.saved` without values). The supervisor runs `durable_runtime.py auth <runtime>`, which stops that environment's Auth, renames it to `-previous`, starts a new one with the new environment, waits for `/health`, and on failure removes the new one, renames the old one back and starts it (`reconcile_auth`). Other environments are untouched; the database holds all Auth state, so nothing is lost.
- Owners and admins only (`environmentProject(... ['owner','admin'])`). The GET answer carries `secret_set`, never the secret.
- Gaps: no phone, email-provider, web3 or SAML switches; no email templates; no attack protection (captcha), password rules, MFA settings, hooks; rate limits only for email, otp and verify; the secrets of mail and sign-in are separate files with separate forms; the UI is one long form, not the cloud's page set.

## Principles

- **One owner per key.** A registry maps each platform config key to its `GOTRUE_` variable, type, limits, secrecy, default, the page it appears on, and which file owns it (`auth.json` or `mail.json`). A key has exactly one owner, so two forms can never fight over a variable. The registry is a JSON file read by TypeScript and Python; a parity test fails when either side differs.
- **Strict per environment.** Every path, file and container name carries the runtime id (`e_` plus 24 hex, already enforced by `RUNTIME`). There is no installation wide provider setting and no inheritance: a new environment starts from pinned defaults, never from another environment's file. `SBARBASE_PUBLIC_URL` is the only shared value, and it is an address, not a setting.
- **Secrets stay in the file and the container.** Never in the catalog, never in a log or error (errors name a key), never in an API answer (the answer carries `secret_set`, as `SignIn` does). A secret field in the UI shows a mask; typing replaces it, empty keeps it. Honest limit, as for mail: the value sits in the container's `Config.Env`, so anyone with Docker daemon access can read it.
- **Apply by recreate with rollback**, as today. GoTrue reads its environment at start; no live patch. Cost: that environment's Auth is down for the restart (to be measured and written down, not assumed). One save is one recreate.
- **Owner and admin only** for read of the editable form and for write, as today. Viewers see nothing under Authentication in v1 (INFERRED to be the safe default; the cloud lets a read only role see most pages, to decide after A1).
- **Audit.** Every save records actor, environment and the list of changed key names (never values) in `audit_events`; the Activity page already lists these.
- **Validation is shared.** Site URL, redirect allow list (scheme required, wildcards `*` and `**` allowed, no whitespace or comma), provider URLs (http or https, no credentials in the address), ranges for numbers, secret length caps. Rules live in the registry and are applied in TypeScript (answer 400 naming the field) and again in Python before the environment is written.
- **Open source generality.** Nothing assumes the owner's server, domain or provider. Callback URLs derive from `SBARBASE_PUBLIC_URL`.

## Phases

Each phase is a checkpoint (sbar-checkpoint): source change, tests bound to the source, an independent review, one commit. Reader docs and console copy are bilingual in the same change as each phase ([ARABIC-DOCS](../ARABIC-DOCS.md)); CHANGELOG entries follow each phase.

- **A0, registry and read side (first).** Registry JSON for the core keys, sessions, the 19 providers (labels, descriptions and fields from the cloud forms), SMTP summary and rate limits. `GET /management/v1/environments/{id}/auth-config` returns the cloud shaped object for one environment: saved values over pinned defaults, secrets masked as `secret_set`, the callback URL per provider, and the applied state. A read only Authentication section in the console shows it grouped like the cloud. Proof: unit tests for masking and defaults; a test that two environments never see each other's values; role test (viewer 403); the answer for an environment with no file equals pinned defaults; a live read of one real environment in the lab.
- **A1, providers and URL configuration, write.** Replace the long sign-in form with the cloud's Sign In / Providers page (User Signups toggles, Auth Providers list with expandable rows, Email, Phone, Anonymous, Web3 switches where the pinned Auth has them) and URL Configuration (Site URL, Redirect URLs). Add the providers the cloud lists that the pinned Auth supports (for example Azure with tenant URL, Apple, Twitter, WorkOS, Keycloak already exist; Phone and Web3 switches are new). Registry live probe: for every registry key set the variable on a throwaway Auth and read the effect from `GET /settings` or behavior, one container at a time (this is what makes the `GOTRUE_` mapping VERIFIED instead of INFERRED). Isolation proof: two environments in one installation, a provider set on A, then B's file, B's container environment, B's API answers and B's `/settings` hold none of it.
- **A2, Sessions, Rate Limits, Attack Protection, Passwords, MFA.** Session lifetimes exist; add single session per user and refresh token reuse interval if supported, the full rate limit set (email, sms, token refresh, verify, otp, anonymous, web3), captcha (`SECURITY_CAPTCHA_*` with secret), password minimum length and required characters, leaked password protection, MFA toggles and notifications. Each page confirms what the pinned GoTrue does not support instead of hiding it.
- **A3, Email.** Email templates (confirmation, invite, magic link, change, recovery, reauthentication and the notification templates the pinned Auth has) with the cloud's variable list and a reset to default; SMTP page over the existing mail file (one owner: `mail.json`; the Authentication workspace is a front end, the old mail command keeps working). Template content is data, size capped, rendered only by Auth.
- **A4, Phone and Hooks.** SMS providers (Twilio, Twilio Verify, MessageBird, Textlocal, Vonage) with their secrets, test OTP; Auth Hooks (HTTP URI plus signing secret, Postgres function). Hooks can call out, so egress rules for the Auth container are checked first ([ENVIRONMENT-EMAIL](../ENVIRONMENT-EMAIL.md) already has Auth egress for mail).
- **A5, SAML and third party.** Study first: `SAML_ENABLED` is an environment setting but SSO providers are stored through the Auth admin API, which the console does not call today. Decide by experiment; may stay out of scope. Third-party auth (external JWT issuers) the same.
- **A6, acceptance.** Live isolation check with two environments through the real console and gateway, secret leak scan of API answers, logs, catalog and audit, rollback check (an invalid provider URL that starts but fails health, an Auth that does not start), measured Auth downtime per save, docs and evidence committed.

## Review findings folded in

An independent design review (EGM, read only, against the code) found these. Each is verified in the code it names and changes the plan as below. Where a phase text above disagrees, this section wins.

1. **Ownership is by prefix lists today, so "one owner per key" must become code.** `is_mail_key` (`lab/durable_runtime.py:40`) claims `GOTRUE_SMTP_`, `GOTRUE_MAILER_` and `GOTRUE_RATE_LIMIT_`; `OWNED_PREFIXES` (`lab/auth_settings.py:60`) covers only the sign-in keys. New keys (`PASSWORD_`, `SECURITY_CAPTCHA_`, `MFA_`, `HOOK_`, `SMS_`, the sms, refresh, anonymous and web3 rate limits, `MAILER_TEMPLATES_`) fall in the mail prefixes or in none, so a retained Auth would hit "runtime drift" or be recreated by the wrong owner. Overlaps that exist now: `GOTRUE_MAILER_TEMPLATES_MAGIC_LINK` and `GOTRUE_MAILER_AUTOCONFIRM` (forced true in `lab/run.py`, set by `mail.json autoconfirm`, and the cloud's "Confirm email" is its inverse), and the three mail rate limits. Decision: the registry carries an `owner` for every key; `owned()`, `is_mail_key` and the `launch` stale rule are generated from it; a test proves the owner sets are disjoint and every registry key has exactly one owner. Overlaps are assigned in A1 (the three rate limits, autoconfirm and the magic link template move to `auth.json` with a `mail.json` migration, or stay mail owned and read only on the Auth pages; decided then, never both). Also, `mail.json` needs every key, so a user without SMTP cannot change them today; moving them fixes that.
2. **Fail closed is false today.** `load_settings` (`lab/durable_runtime.py:334`) swallows a bad file and returns None, and feeds every start, the rolling replacement and `reconcile_mail`, so one bad file restarts that Auth on defaults. Gate: those paths fail closed (keep the running Auth, or use the last applied copy). The file gets a `version`; `validate` accepts older versions, and a downgrade test proves a newer file does not make every environment restart on defaults. This is **A0.5, before any write phase.**
3. **Email templates have no delivery path.** The cloud keys are inline bodies (`MAILER_TEMPLATES_*_CONTENT`); the pinned Auth takes a URL fetched at send time (`mail_config.py`, `run.py:188`). Storing bodies in `auth.json` cannot work (64 KB cap, env file). A3 first decides: a per environment internal template endpoint reachable only by that environment's Auth on an unguessable path, or URL only fields like the cloud's external templates, or unsupported. The A1 probe also records name mismatches (`*_CONTENT`, X and TWITTER, SLACK and SLACK_OIDC).
4. **SMTP has no console write path and its apply has no rollback.** There is no mail route in `src/`; `reconcile_mail` is CLI only and does `docker rm -f` before launch, so a failed start leaves no Auth. The SMTP password also deliberately never crosses the management API today (the host command in the console). A3 therefore: one swap style apply (`reconcile_auth`) loading both files, one pending revision for both, and an owner decision on the SMTP password (sign-in provider secrets already cross the API, so the precedent exists, but it is a change to a recorded design). Until decided SMTP stays read only plus the host command.
5. **A save during an apply is lost, and concurrent saves clobber.** `record()` updates by runtime only and overwrites a newer pending revision with `applied`; `PUT` has no base revision. Fix in A0.5: the client sends the base revision and the server answers 409 on mismatch; `record()` is conditional on `revision <= applied revision`; a test saves mid apply.
6. **Rollback gaps.** A kill between `rename` and launch leaves only `...-auth-previous`; a failed rollback health wait leaves Auth down; the failed file stays as the desired state so the next start retries it; `launch` overwrites the private env file with the failed config. Fix: a last good copy (`<runtime>-auth.applied.json`) that starts use after a failure, the failed file marked failed, startup recovery for a stray `-previous`, and a kill mid swap case in A6.
7. **Global operation lock and tenant starvation.** Each save holds the installation wide lock for stop, boot and health wait; `PUT` has no throttle. Fix: a per environment minimum save interval, coalescing on revision, and measured lock hold time. Auth downtime per save moves from "not established" to an A1 gate.
8. **Egress review moves to A1.** Provider URLs (Azure, GitLab, Keycloak, WorkOS) and later template and hook URLs cannot be proven safe by string checks; Auth sits on the shared runtime network by default. A1 designs default deny egress for the Auth container with the `mail_egress` mechanism and an allow list, and tests that a provider URL pointing at another environment's container is unreachable. This is INFERRED from the code and must be tested first.
9. **A0 ships only mappings already verified.** The keys A0 shows are the ones `lab/auth_settings.py` already writes and `lab/sign-in-check.ts` covers live; the one inferred default is `JWT_EXP` 3600 (the pinned Auth's own default, to be confirmed by the probe). Every later key enters the registry only after the live probe, and carries `verified: true`. The classifier derivation and disjointness test from item 1 start in A0.5.
10. **Secret handling gaps.** The TypeScript reader follows symlinks and skips the mode check `mail_config.load` does; a crash leaves `<runtime>-auth.json.pending`; the private env file is a third copy not in the leak scan; no code removes the per environment secret files on purge; `-mail.json` may be missing from the recovery materials. Fix: symlink and mode checks in the reader, remove `.pending` at start, include the env file and `-previous` in the leak scan, purge every per runtime secret file with the environment, and verify both files are in the recovery inventory. Checked in A0.5 and A6.
11. **No way to clear a secret.** Empty keeps it. Add an explicit clear flag for secrets that are not tied to enabling a provider (captcha, SMS, hooks).
12. **Validation parity needs vectors, and the audit needs a diff.** TypeScript uses `new URL`, Python `urlsplit`; they differ on edge inputs. Require a shared vector file both test suites run. The audit event records only `{revision}` today; "changed key names" needs a diff computed before the write, specified in A1.

Revised order: **A0** (read side, shipped first) then **A0.5** (items 2, 5, 6, 10 and the classifier work of 1: no new setting until saving is safe) then **A1** to **A6** with items 1, 3, 4, 7, 8, 11 and 12 inside them as written above.

## Security gates

1. **No secret outside file and container.** A test greps every API answer, log line, audit row and catalog column of a saved environment for the secrets used in the test.
2. **Isolation.** The A1 two environment proof, repeated in A6 through the console.
3. **Rollback.** A save that leaves Auth unhealthy leaves the previous Auth running and shows the failure (extends `lab/sign-in-check.ts`).
4. **Role.** Viewer and non member get 403 and 404 as today, on every new route.
5. **Redirect safety.** The allow list never accepts a bare wildcard host or a scheme without `://`; document that `**` is the cloud's own semantics.
6. **Write only after validation on both sides**, and a file that fails validation at load fails closed (the environment keeps its running Auth).
7. **Operation lock.** One runtime operation at a time per installation (existing lock); a busy answer is retried, not forced.
8. **Egress for hooks and SMS** reviewed before A4 ships.

## Tests and evidence

Bun tests for the registry, masking, views, routes and roles; Python tests for registry parity, `configuration` mapping and validation; `lab/sign-in-check.ts` extended for the new keys; docs tests (`lab/test_docs_bilingual.py`, links, no long dashes) updated for each new reader page; typecheck of `ui/`. Live probes write source bound JSON under `docs/evidence/` with their scope. Machine load rule: one container at a time, no parallel suites.
