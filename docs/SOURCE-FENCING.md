# Source database fence

`lab/source_fence.py` provides trusted operator operations for the local PostgreSQL candidate. `fence` persists ALLOW_CONNECTIONS=false for one validated environment database before terminating its existing backends. It waits for zero sessions, verifies the persisted refusal and refuses successful completion if prepared transactions remain. A termination failure leaves the database closed rather than reopening it automatically. `unfence` is a separate explicit operator rollback.

The durable installer refuses to reprovision a fenced database. Normal startup skips fenced environments rather than clearing their protection. This is PostgreSQL state, so it survives controller and database restart independently of gateway maintenance metadata. It is not an HTTP endpoint, and no production environment was fenced in this change.

All 49 Python tests pass, including fence ordering, termination failure, invalid identifiers and installer refusal. Eight live checks used a disposable database on the retained target: an active session was terminated, new connections including the privileged operator were rejected, a neighboring retained environment stayed readable, restart retained refusal, explicit rollback restored connectivity, and the disposable database was removed before stopping the target. The source and restored environment data were not modified.

This boundary stops database sessions, not every external side effect. A Storage request authorized before fencing could still write files or S3 objects. Full cutover must combine persistent gateway maintenance, drain across all gateway workers, database fencing, Storage quiescence, a consistent final export and target validation. Already-exported recovery data may be stale relative to later source activity. Administrative operators can intentionally clear the database flag; malicious host administrators are outside this trust boundary. Background/external integrations require separate inventory and fencing. Automatic coordinated cutover is still unfinished.

## Export access while services are fenced

A fully closed database rejects pg_dump too. `prepare_export` therefore records the original three service-login flags before transactionally changing them to NOLOGIN, terminates remaining environment sessions and verifies zero active sessions. Trusted local operator access remains for metadata reads and pg_dump. The durable installer now treats either database refusal or a disabled scoped service login as fenced, so a restart cannot silently reenable the environment. Failures leave login refusal and a journal for explicit reconciliation. Clearing only ALLOW_CONNECTIONS is insufficient to roll back this two-stage fence; original login flags must also be restored deliberately from the journal after checking placement.

`recovery-export.py --cutover` opts into this fence after stopping source services and capturing original role attributes. The payload retains pre-fence login intent for the target. After encrypted archive/key persistence, it applies the full database fence and marks the journal exported-and-fenced. Default export behavior remains unchanged. The cutover mode has not yet run against the real source or been integrated with catalog maintenance. It must not be treated as complete cutover automation.

All 51 Python tests pass. Eight live disposable-fixture checks verify baseline service access, denial after NOLOGIN, continued operator access and successful pg_dump, recorded login intent, installer detection and final operator denial. Temporary roles/database/HBA rule were removed and the target stopped. This validates the fence mechanics, not the full encrypted-export path. Source credentials and databases were unchanged.
