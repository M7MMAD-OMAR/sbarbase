# سجل القرارات

سُجّل في 2026-09-20. هذه خلاصات بحث موجزة، وليست شهادة جاهزية للإنتاج. التفاصيل ومصادرها في المراجعات المرتبطة.

| الموضوع | الموقف الحالي وسببه | البديل ولماذا لم يُختر الآن |
|---|---|---|
| الأساس | الإبقاء على Supabase: طلب صريح من المستخدم، وتوافق مع التطبيقات القائمة | Nhost أو Auth مكتوب من الصفر يغيّران عقد API وSDK المطلوب |
| الهرمية | التثبيت > المنظمة > المشروع > البيئة؛ والملكية مستقلة عن مكان التشغيل | ربط المنظمة بالخادم يصعّب نقل الملكية وموازنة السعة |
| حدود قاعدة البيانات | تجربة قاعدة بيانات لكل بيئة على PostgreSQL مشترك | مخطط لكل مشروع يعطي فصلًا أضعف لدورة الحياة المستقلة المطلوبة؛ والنسخ الكاملة تبقى أساس المقارنة في الكلفة |
| أدوار API | اختبار الأدوار القياسية بصفة NOLOGIN مع حسابات دخول فريدة لكل خدمة، وقواعد HBA دقيقة لكل حساب وقاعدة، وصلاحيات CONNECT | الأدوار ذات الأسماء الخاصة بكل بيئة قد تكسر سياسات SQL القائمة؛ وPostgreSQL المستقل هو الخيار الاحتياطي، وليس مرفوضًا |
| Auth وREST | عمليات الخدمات الأصلية لكل بيئة | تبديل قاعدة البيانات وقت الطلب ليس وضعًا مدعومًا راسخًا؛ وإعادة كتابة Auth تضيف مخاطر أمنية ومخاطر توافق |
| الخدمات الأخرى | المشاركة مشروطة باجتياز اختبارات دمج وعزل على إصدار مثبّت. وStudio مكوّن من هذا النوع: يُعتمد لكل بيئة، مثبّت الإصدار، مع نسبته إلى أصحابه، ومختبر بالدمج كما Auth وREST | لا يُستنتج من دعم الإعدادات متعددة المستأجرين أن الدمج آمن |
| واجهة الإدارة | كل بيئة تُدار عبر Supabase Studio الأصلي (upstream)، مثبّت الإصدار، بنسخة واحدة من Studio وأخرى من postgres-meta لكل بيئة. لوحة الإدارة المبنية محليًا تبقي فقط المنظمات والمشاريع والبيئات وتفاصيل الاتصال والمفاتيح وحالة التجهيز، ثم تسلّم إلى Studio | لوحة محلية تقلّد Studio: تكرر ميزات الأصل، وتبتعد عنه مع كل إصدار جديد، ولا تبلغ مستوى Studio الحقيقي |
| المشاريع القائمة | تقييم supabase-multitenant للتكييف، وPigsty للتشغيل | لم يُعتمد أي منها. مشاركة بيانات الاعتماد في Supafleet CLI تحتاج تصحيحًا. Coolify وDokploy يديران النشر لكنهما لا يبنيان هذه البنية المشتركة |
| السعة | قياس أحمال الذروة وحجز هامش للاستعادة قبل القبول | لا 500 زائر يومي ولا عدد الحاويات يتنبأ بالعتاد المطلوب؛ ولا ضمان ثابتًا لـ 10 أو 100 |
| الاستعادة | الاستعادة إلى هدف معزول، ثم التحقق، ثم التحويل؛ مع الكائنات والإعدادات | النسخ المتماثل ليس نسخًا احتياطيًا. الاستعادة الفيزيائية إلى نقطة زمنية تستهدف العنقود كله؛ والاستعادة لكل بيئة تحتاج استخراجًا عبر عنقود مؤقت |
| مخزن التحكم المحلي | محوّل SQLite لبصمات المفاتيح في هذه التجربة | ليس قرارًا نهائيًا لمخزن متعدد الخوادم؛ وقواعد بيانات التطبيقات تبقى PostgreSQL |
| بيئة العمل | تجارب محلية معزولة ومحدودة دون بنية تحتية مستأجرة | شراء VPS والنشر البعيد غير ضروريين قبل اجتياز بوابات الجدوى |

## أعد النظر في هذا الخيار إذا

- تعذّر على SQL الأصلي الكامل أو خطوات الإقلاع أو الترقيات الحفاظ على أدوار قياسية متوافقة بأمان.
- استطاعت بيانات اعتماد خدمة مخترقة عبور حدود البيئة.
- استطاعت بيئة واحدة استنفاد الموارد المشتركة دون قبول واحتواء فعّالين.
- عجز النسخ الاحتياطي والاستعادة أو الترحيل عن بلوغ هدف استعادة مختار صراحة.
- لم يبرر التوفير المقيس تعقيد التشغيل مقارنة بالنسخ المستقلة.
- تعذّر تقديم Studio مثبّت الإصدار لكل بيئة دون كلفة موارد غير مقبولة، أو تطلّب تقديمه تفريع (fork) واجهة الإدارة.
