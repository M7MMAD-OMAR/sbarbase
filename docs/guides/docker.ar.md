# التثبيت عبر Docker

المسار الأساسي هو `deploy/compose.sh`، ويفحص مدخلات المضيف قبل أي بناء أو سحب صور أو تشغيل عبر Compose. المرشح الأول Linux x86_64 مع Docker محلي بصلاحيات root وcgroup v2 والقدرات المطلوبة للموارد وrunc وseccomp الافتراضيين. تأتي Python وBun داخل الصورة؛ يحتاج المضيف POSIX shell وDocker/Compose وأدوات Linux العامة فقط. **اعتماد توافق المضيف والإنتاج غير مثبتين** حتى التثبيت النظيف وقياس الحدود وإعادة الإقلاع والاستعادة الكاملة فعلياً. راجع [عقد الفحص المسبق](../engineering/HOST-PREFLIGHT.md) للمتطلبات والأسباب وحدود الأدلة.

اختر حجم الخادم أولًا من [اختيار خادم](choosing-a-server.ar.md).

## 1. جلب الشيفرة والتشغيل

```bash
git clone https://github.com/M7MMAD-OMAR/sbarbase /opt/sbarbase
cd /opt/sbarbase
deploy/compose.sh check
deploy/compose.sh up
```

صدّر مدخلات النشر صراحةً قبل launcher. يختار ملف Compose من هذا المستودع والمقبس المحلي واسم المشروع، ولا يقرأ `.env`. المدخلات الأساسية هي `SBARBASE_ROOT` و`SBARBASE_DOCKER_SOCKET` و`SBARBASE_DOCKER_DATA_ROOT` واسم مشروع Compose ومنافذ الواجهة وقاعدة البيانات وعنوان الربط و`SBARBASE_PUBLIC_URL`. القيم الافتراضية العامة موثقة في العقد؛ لا يعتمد المسار على مجلد مستخدم أو إعداد جهاز بعينه. يجب أن يطابق `DOCKER_HOST` المقبس المعلن، وترفض إعدادات context/TLS/API وملفات أو profiles بديلة. `check` للقراءة فقط ولا ينشئ مسارات أو volumes أو حاويات أو يثبت حزماً. الأمر المباشر `docker compose up` يتجاوز فحص المضيف.

التشغيل الأول يسحب صور Supabase المثبّتة (نحو 2.4 GB) ويستغرق بضع دقائق. تابعه بالأمر `deploy/compose.sh logs`؛ يصبح جاهزًا عندما يظهر في السجل `Local Sbarbase API: http://127.0.0.1:8790`.

## 2. إنشاء أول مشغّل

```bash
deploy/compose.sh bootstrap
```

يحافظ أمر bootstrap المحدد على المقبس ومسار المستودع واسم المشروع اللذين اختارهما launcher. يسأل عن بريد إلكتروني واسم عميل (مؤسسة) وكلمة مرور لا تظهر أثناء كتابتها. بعدها افتح الواجهة على `http://127.0.0.1:8790` على الخادم (مثلًا عبر `ssh -L 8790:127.0.0.1:8790 your-server`)، وسجّل الدخول، وأنشئ مشروعًا وبيئة، وانسخ بيانات الاتصال والمفتاح.

## 3. وضع HTTPS أمامه

الواجهة والـ API تستمعان على loopback فقط. انشرهما عبر وكيل TLS الموصوف في [نشر الخادم](server-deployment.ar.md)، أو أي reverse proxy تستخدمه أصلًا، موجّهًا إلى `127.0.0.1:8790`.

## أوامر يومية

| المهمة | الأمر |
|---|---|
| الحالة والسجلات | `deploy/compose.sh ps`، `deploy/compose.sh logs` |
| فحص السلامة | `deploy/compose.sh smoke` |
| إيقاف كل شيء بنظافة | `deploy/compose.sh down` |
| التشغيل من جديد | `deploy/compose.sh up` |
| تحديث صباربيز | صفحة التحديثات في لوحة الإدارة، أو قسم التحديثات أدناه |
| النسخ الاحتياطي والاستعادة | راجع [النسخ الاحتياطي والاستعادة](backup-and-restore.ar.md)؛ النسخ اليومي يعمل وحده |

الإعداد `restart: unless-stopped` يعيد صباربيز بعد إعادة تشغيل الخادم، بشرط أن يبدأ Docker نفسه عند الإقلاع (باستخدام مدير الخدمات الخاص بتوزيعة المضيف). البيانات محفوظة في volumes الخاصة بـ Docker وفي المجلدين `.lab/` و`.secrets/` داخل نسخة المستودع، والأمر `deploy/compose.sh down` يحتفظ بها كلها.

## التحديثات

تعرض صفحة التحديثات في لوحة الإدارة الإصدار الموقّع الأحدث، وتثبّت الآمن منه بنقرة واحدة، وتثبّت الإصدار الذي يغيّر Auth أو Storage أو Realtime بعد أن تؤكد تحذيرًا ([الترقيات](upgrades.ar.md)). ينتظر المشرف انتهاء العمل الجاري، ويأخذ نسخة احتياطية من كل بيئة، وينقل نسخة المستودع، ويتوقف بترتيب، ثم يخرج برمز 42. يعيد الإعداد `restart: unless-stopped` تشغيل الحاوية عند أي خروج وبالصورة نفسها. يبدأ سكربت الحاوية بفحص profile المثبت داخل الصورة قبل حارس الترقية، ويعيد الفحص بعده، ثم يحجز الإصدار الجديد حركة التطبيقات حتى يجتاز فحوص السلامة. وإن لم يجتزها عاد وحده، وأُعيد تشغيل الحاوية مرة أخرى على الإصدار السابق؛ ويعود الحارس أيضًا بعد 3 مرات تشغيل فاشلة، أو بعد تشغيل مات في منتصفه.

إعدادان في `compose.yaml` يخصّان التحديثات. يضبط `TZ` المنطقة الزمنية للحاوية، وبها تُقرأ نافذة الصيانة للتحديث التلقائي (UTC إن لم يُضبط؛ والصورة تحمل قاعدة بيانات المناطق الزمنية، فيعمل اسم مثل `Asia/Dubai`). ويوجّه `SBARBASE_RELEASE_SOURCE` فحص التحديثات إلى مرآة؛ اتركه فارغًا للمستودع الرسمي.

إعادة التشغيل العادية تستخدم الصورة نفسها والحاوية التي أنشأها `compose.yaml`. والإصدار الذي صنفه "يحتاج إعادة بناء" يغيّر أحدهما، فيُثبَّت على الخادم ثم يُعاد بناء الحاوية:

```bash
deploy/compose.sh upgrade vX.Y.Z
deploy/compose.sh up
```

لا تحدّث بالأمر `git pull`: فهو يتجاوز النسخة الاحتياطية ولقطة التحكم والعودة. والانتقال إلى أول إصدار فيه قناة التحديث يحتاج إعادة بناء أيضًا، وخطواته في [دليل الترقيات](upgrades.ar.md). شُغّلت قناة التحديث في CI وفي آلة افتراضية محلية في 26 سبتمبر 2026، مع إصدارات موقّعة مؤقتة وتثبيت وتراجع عن إصدار معطوب ([دليل التجربة](../evidence/vm-channel-checks.json)). يثبت ذلك نطاق التجربة فقط؛ ولم يُعتمد إصدار جديد من Supabase، ولم تُختبر القناة على خادم مستقل منشور للناس.

## كيف تتركب القطع

تحمل الحاوية طبقة التحكم: المشرف، وعامل التجهيز، والواجهة، والبوابة. وهي تشغّل خدمات Supabase المثبّتة كحاويات مجاورة عبر مقبس Docker على الخادم. ثلاثة إعدادات في `compose.yaml` تجعل ذلك يعمل، ويحافظ عليها اختبار:

- نسخة المستودع مركّبة على المسار نفسه كما على الخادم، والحاوية تستخدم شبكة الخادم، فالمسارات وعناوين loopback تعني الشيء نفسه داخلها وخارجها؛
- مجلد بيانات Docker المعلن مركّب للقراءة فقط، حتى تُطبَّق حدود القرص على القرص الذي يحمل بيانات Docker؛
- الإعداد `init: true`، لأن المشرف يرفض أن يعمل كعملية رقم 1.

الوصول إلى مقبس Docker يعادل صلاحية root على الخادم، كما في التثبيت عبر systemd؛ [نموذج التهديدات](../explain/threat-model.ar.md) يشرح لماذا يُقبل ذلك حاليًا.

يجهّز بدء الخدمة `.secrets` و`.secrets/upstream` بالصلاحية `0700` وملكية حساب الخدمة. تُرفض المجلدات الموجودة بملكية أو صلاحيات مختلفة والروابط الرمزية؛ راجع [إصلاح صلاحيات مجلد الأسرار](server-deployment.ar.md#صلاحيات-مجلد-الأسرار) قبل إعادة تشغيل نسخة قديمة مرفوضة.
