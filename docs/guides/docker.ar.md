# التثبيت عبر Docker

أقصر طريق: أي خادم Linux عليه Docker Engine مع إضافة Compose. تأتي Python وBun وأداة Docker داخل صورة صباربيز، فلا يهم إصدار Python على الخادم نفسه. يشغّل CI هذا المسار نفسه على جهاز نظيف مع كل تغيير: البناء والتشغيل، ثم أول مشغّل، ثم أول مشروع يُستخدم عبر supabase-js، ثم نسخة احتياطية واستعادة، ثم إعادة تشغيل، ثم إيقاف نظيف.

اختر حجم الخادم أولًا من [اختيار خادم](choosing-a-server.ar.md).

## 1. جلب الشيفرة والتشغيل

```bash
git clone https://github.com/M7MMAD-OMAR/sbarbase /opt/sbarbase
cd /opt/sbarbase
docker compose up -d --build
```

التشغيل الأول يسحب صور Supabase المثبّتة (نحو 2.4 GB) ويستغرق بضع دقائق. تابعه بالأمر `docker compose logs -f`؛ يصبح جاهزًا عندما يظهر في السجل `Local Sbarbase API: http://127.0.0.1:8790`.

## 2. إنشاء أول مشغّل

```bash
docker compose exec sbarbase python3 lab/bootstrap.py
```

يسأل عن بريد إلكتروني واسم عميل (مؤسسة) وكلمة مرور لا تظهر أثناء كتابتها. بعدها افتح الواجهة على `http://127.0.0.1:8790` على الخادم (مثلًا عبر `ssh -L 8790:127.0.0.1:8790 your-server`)، وسجّل الدخول، وأنشئ مشروعًا وبيئة، وانسخ بيانات الاتصال والمفتاح.

## 3. وضع HTTPS أمامه

الواجهة والـ API تستمعان على loopback فقط. انشرهما عبر وكيل TLS الموصوف في [نشر الخادم](server-deployment.ar.md)، أو أي reverse proxy تستخدمه أصلًا، موجّهًا إلى `127.0.0.1:8790`.

## أوامر يومية

| المهمة | الأمر |
|---|---|
| الحالة والسجلات | `docker compose ps`، `docker compose logs -f` |
| فحص السلامة | `docker compose exec sbarbase python3 lab/install_server.py smoke` |
| إيقاف كل شيء بنظافة | `docker compose down` |
| التشغيل من جديد | `docker compose up -d` |
| تحديث صباربيز | صفحة التحديثات في لوحة الإدارة، أو قسم التحديثات أدناه |
| النسخ الاحتياطي والاستعادة | راجع [النسخ الاحتياطي والاستعادة](backup-and-restore.ar.md)؛ النسخ اليومي يعمل وحده |

الإعداد `restart: unless-stopped` يعيد صباربيز بعد إعادة تشغيل الخادم، بشرط أن يبدأ Docker نفسه عند الإقلاع (`systemctl enable docker`). البيانات محفوظة في volumes الخاصة بـ Docker وفي المجلدين `.lab/` و`.secrets/` داخل نسخة المستودع، والأمر `docker compose down` يحتفظ بها كلها.

## التحديثات

تعرض صفحة التحديثات في لوحة الإدارة الإصدار الموقّع الأحدث، وتثبّت الآمن منه بنقرة واحدة ([الترقيات](upgrades.ar.md)). يأخذ المشرف نسخة احتياطية من كل بيئة، وينقل نسخة المستودع، ويتوقف بترتيب، ثم يخرج برمز 42. يعيد الإعداد `restart: unless-stopped` تشغيل الحاوية عند أي خروج وبالصورة نفسها، ثم يحجز الإصدار الجديد حركة التطبيقات حتى يجتاز فحوص السلامة. وإن لم يجتزها عاد وحده، وأُعيد تشغيل الحاوية مرة أخرى على الإصدار السابق.

إعادة التشغيل العادية تستخدم الصورة نفسها والحاوية التي أنشأها `compose.yaml`. والإصدار الذي صنفه "يحتاج إعادة بناء" يغيّر أحدهما، فيُثبَّت على الخادم ثم يُعاد بناء الحاوية:

```bash
docker compose exec sbarbase python3 lab/upgrade.py start --release vX.Y.Z --allow-class rebuild
docker compose up -d --build
```

لا تحدّث بالأمر `git pull`: فهو يتجاوز النسخة الاحتياطية ولقطة التحكم والعودة. والانتقال إلى أول إصدار فيه قناة التحديث يحتاج إعادة بناء أيضًا، وخطواته في [دليل الترقيات](upgrades.ar.md). لا تغطي قناة التحديث حتى الآن إلا اختبارات الوحدات: لم تُشغَّل بعد حالات CI الحية الخاصة بها ولا تجربتها الكاملة في الآلة الافتراضية.

## كيف تتركب القطع

تحمل الحاوية طبقة التحكم: المشرف، وعامل التجهيز، والواجهة، والبوابة. وهي تشغّل خدمات Supabase المثبّتة كحاويات مجاورة عبر مقبس Docker على الخادم. ثلاثة إعدادات في `compose.yaml` تجعل ذلك يعمل، ويحافظ عليها اختبار:

- نسخة المستودع مركّبة على المسار نفسه كما على الخادم، والحاوية تستخدم شبكة الخادم، فالمسارات وعناوين loopback تعني الشيء نفسه داخلها وخارجها؛
- المجلد `/var/lib/docker` مركّب للقراءة فقط، حتى تُطبَّق حدود القرص على القرص الذي يحمل بيانات Docker؛
- الإعداد `init: true`، لأن المشرف يرفض أن يعمل كعملية رقم 1.

الوصول إلى مقبس Docker يعادل صلاحية root على الخادم، كما في التثبيت عبر systemd؛ [نموذج التهديدات](../explain/threat-model.ar.md) يشرح لماذا يُقبل ذلك حاليًا.
