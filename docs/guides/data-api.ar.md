# واجهة البيانات (Data API)

واجهة البيانات هي PostgREST الخاص بالبيئة، أي ما يصل إليه `supabase.from()` و`supabase.rpc()`. لا تخدم في الأصل إلا المخطط `public`. إذا كان تطبيقك يحفظ جداوله في مخطط خاص به، فاكشف هذا المخطط هنا، كما تفعل في إعدادات Data API في Supabase.

## اكشف مخططًا

1. أنشئ المخطط وجداوله أولًا، بملف ترحيل أو من Studio. لا يُكشف مخطط غير موجود بعد.
2. امنح أدوار الواجهة صلاحية الوصول إليه، كما في Supabase:

```sql
grant usage on schema app to anon, authenticated, service_role;
grant select, insert, update, delete on all tables in schema app to anon, authenticated, service_role;
grant usage, select on all sequences in schema app to anon, authenticated, service_role;
grant execute on all functions in schema app to anon, authenticated, service_role;
alter table app.items enable row level security;
```

3. افتح البيئة في لوحة الإدارة، ثم **Database connection**، ثم **Data API**. اكتب في **Exposed schemas** المخططات بالترتيب، مثل `public, app`، واضغط **Save Data API settings**. تظهر **Applying…** ثم **Applied**، وعادةً خلال ثوانٍ. لا يُعاد تشغيل الواجهة.

أول مخطط في القائمة هو المخطط الافتراضي. وتصل إلى البقية من supabase-js هكذا:

```js
const { data } = await supabase.schema('app').from('items').select()
```

أو بالترويسة `Accept-Profile: app` للقراءة و`Content-Profile: app` للكتابة.

اترك **Exposed schemas** فارغًا لإيقاف واجهة البيانات: يجيب كل جدول عندها بـ 404، وتعرض لوحة الإدارة **Off**.

أما **Extra search path** فهو المكان الذي يبحث فيه PostgREST عن الأنواع والدوال التي يستخدمها الاستعلام دون اسم مخطط، مثل `public, extensions`. ويضع **Maximum rows per request** حدًا لعدد الصفوف في كل جواب، واتركه فارغًا إن لم ترد حدًا.

## من Supabase CLI أو من وكيل

الإعدادات نفسها متاحة عبر `GET` و`PATCH /v1/projects/{ref}/postgrest`، وهي نقطة Management API في Supabase لقسم `[api]` في `config.toml`. يجيب `GET` بما تخدمه الواجهة الآن، ويظهر فيه التغيير بعد تطبيقه:

```toml
[api]
schemas = ["public", "app"]
extra_search_path = ["public", "extensions"]
max_rows = 1000
```

ولا يغيّر `PATCH` إلا الحقول التي يذكرها. لا يحوي الجواب سر التوقيع أبدًا. ويجيب بالرمز `200` ما إن يُحفظ التغيير؛ فإن رفضته قاعدة البيانات بعد ذلك، لأن مخططًا غير موجود مثلًا، يظل `GET` يعرض المخططات السابقة، ويظهر السبب في لوحة الإدارة وحدها. ولا يجوز أن يكون مسار البحث الإضافي فارغًا (يرسل `supabase config push` القيمة `""` للقائمة `[]`: اكتب `public` بدلًا منها). ويقرأ رمز الوصول المخصص للقراءة الإعدادات دون أن يغيّرها. انظر [الوكلاء](agents.ar.md).

## ما يُرفض

- مخطط غير موجود في قاعدة بيانات البيئة. تذكر لوحة الإدارة اسمه وما يُخدم حاليًا، ولا يتغير شيء، حتى بعد إعادة التشغيل.
- مخططات المنصة، مهما كانت الصلاحيات: `auth` و`storage` و`vault` و`realtime` و`_realtime` و`extensions` و`cron` و`net` و`graphql` و`pgmq` و`pgsodium` و`pgsodium_masks` و`pgtle` و`pgbouncer` و`etl` و`_analytics` و`_supavisor` و`supabase_functions` و`supabase_migrations` و`information_schema`، وكل ما يبدأ بـ `pg_` أو `sbarbase` أو `supabase`. كشف أي منها ينشر المستخدمين أو الملفات أو الأسرار.
- الأسماء التي تحتاج إلى علامات اقتباس: استخدم حروفًا لاتينية صغيرة وأرقامًا وشرطة سفلية، وابدأ بحرف أو بشرطة سفلية.
- المخطط `graphql_public`، لأن GraphQL لا تُخدم. يذكره `config.toml` في Supabase افتراضيًا، فاحذفه قبل `supabase config push`.
- أكثر من 16 مخططًا، أو المخطط نفسه مرتين.

ما دام المخطط مكشوفًا، أو مذكورًا في مسار البحث الإضافي، ترفض قاعدة بيانات البيئة إعادة تسميته أو حذفه. فما إن يختفي مخطط مكشوف واحد حتى يتوقف PostgREST عن الرد على كل الطلبات، لا على طلبات ذلك المخطط وحده. احذفه من **Exposed schemas** أولًا، وانتظر **Applied**، ثم أعد تسميته أو احذفه. وتعمل إعادة تسمية أي مخطط أو حذفه بمستوى العزل read committed، وهو الافتراضي في PostgreSQL، وتُرفض داخل معاملة `repeatable read` أو `serializable`.

وعند تشغيل البيئة أو استعادتها يكتب صباربيز من جديد آخر إعدادات طُبّقت، وإن كانت إحدى جلسات قاعدة بياناتك تمسك في تلك اللحظة قفل واجهة البيانات الخاص بالمنصة فإنها تُنهى. وإن اختفى مخطط رغم ذلك، بعد استعادة نسخة احتياطية أقدم مثلًا، يخدم صباربيز بقية المخططات عند تشغيل البيئة، ويذكر القسم المخطط الذي استُبعد. أنشئه من جديد، ثم أعد تشغيل صباربيز أو احفظ الإعدادات ليُخدم. وإن لم يبقَ أي مخطط مكشوف، تجيب الواجهة بـ 404 عن كل جدول، ولا تخدم `public` بدلًا منها. وتحتفظ البيئة المستعادة على تثبيت آخر بالإعدادات التي تحملها قاعدة بياناتها، ما دامت صالحة.

## الحدود

- كشف المخطط لا يمنح أي صلاحية. فدون الصلاحيات أعلاه تجيب الطلبات بـ `permission denied`، ودون أمان الصفوف يقرأ الجدول كل من يملك المفتاح العام.
- لا يفحص مستشار الأمان إلا جداول `public`.
- يحتفظ PostgREST في كل بيئة بثلاثة اتصالات بقاعدة البيانات، ولا يمكن تغيير `db_pool`.
- لا يستطيع كود يعمل بحساب قاعدة بيانات الواجهة في بيئتك، كدالة تعود إلى ذلك الحساب، أن يختار المخطط الذي يُخدم، لكنه يستطيع أن يجعل إعادة التحميل تفشل، فتجيب الواجهة بالرمز `404` عن كل جدول إلى أن يُعاد تشغيل صباربيز. ويبقى ذلك داخل بيئتك ولا يصل إلى شيء من بيئة أخرى.
- يعيد الرجوع إلى إصدار سابق لإعدادات واجهة البيانات إنشاء واجهة كل بيئة بالإعداد القديم، الذي لا يخدم إلا `public`، حتى في بيئة أطفأت فيها واجهة البيانات، إلى أن يعمل الإصدار الأحدث من جديد.
- لا تُخدم GraphQL.
- يُعاد تشغيل جلسة Studio المفتوحة عند تغيير الإعدادات، كي تعرض المخططات نفسها التي تخدمها الواجهة.
- تُحفظ هذه الإعدادات في قاعدة بيانات البيئة نفسها، داخل المخطط `sbarbase_rest` الذي تملكه المنصة، فلا تطّلع عليها أي بيئة أخرى. وأول تشغيل بعد الترقية يعيد إنشاء حاوية الواجهة لكل بيئة مرة واحدة.
