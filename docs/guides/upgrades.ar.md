# الترقيات

## ترقية تثبيت

أمر واحد ينقل التثبيت إلى إصدار أحدث من صباربيز، وإعادة التشغيل تبدأ به. إذا لم يعمل الإصدار الجديد، يعود صباربيز وحده إلى الإصدار السابق. مع Docker ضع `docker compose exec sbarbase` قبل كل أمر `python3`.

| المهمة | الأمر |
|---|---|
| معرفة ما سيتغير، دون تغيير أي شيء | `python3 lab/upgrade.py check` |
| الترقية إلى أحدث إصدار | `python3 lab/upgrade.py start` |
| ثم إعادة التشغيل عليه | `docker compose up -d --build` (أو `sudo systemctl restart sbarbase`) |
| معرفة النتيجة | `python3 lab/upgrade.py status` |
| العودة إلى الإصدار السابق | `python3 lab/upgrade.py rollback`، ثم إعادة التشغيل بالطريقة نفسها |

يذهب `start` إلى `origin/main` افتراضيًا، والخيار `--to <وسم أو commit>` يختار إصدارًا آخر. قبل أن يغيّر أي شيء:

1. يرفض إذا كان في نسخة المستودع تعديلات محلية، أو إذا كان الإصدار الجديد يغيّر صورة PostgreSQL (هذا ترحيل لقاعدة البيانات وليس ترقية، انظر أدناه)؛
2. يسحب كل صورة يثبّتها الإصدار الجديد، فلا يوقف تنزيلٌ ناقص تثبيتًا يعمل؛
3. يأخذ نسخة احتياطية من كل بيئة ([النسخ الاحتياطي والاستعادة](backup-and-restore.ar.md))، وتبقى النسخ بعد الترقية.

عند إعادة التشغيل، تُستبدل فقط حاويات Auth وREST وStorage التي تغيّرت صورتها المثبّتة أو إعداداتها. هذه الحاويات لا تحفظ بيانات خاصة بها: المستخدمون والصفوف والملفات تبقى في قاعدة البيانات ووحدة تخزين الملفات، ولا يمسّها أي شيء. إذا فشل ذلك التشغيل، يعيد المشرف نسخة المستودع إلى الخلف ويخرج، فتعيد سياسة إعادة التشغيل تشغيل الإصدار السابق بصوره السابقة. عندها يعرض `status` الحالة `rolled_back`، والنسخ الاحتياطية المأخوذة قبل الترقية موجودة إن احتجتها.

يشغّل CI هذا على جهاز نظيف مع كل تغيير: ترقية حقيقية إلى PostgREST أحدث، ثم إصدار معطوب لا يعمل أبدًا يعود منه صباربيز وحده، مع مقارنة المستخدمين والملفات وحاويات Storage قبل وبعد.

## تغيير إصدار أصلي مثبّت

هذا القسم لمن يطوّرون المشروع. يشغّل صباربيز صور Supabase الأصلية بإصدارات مثبّتة. تغيير تثبيت واحد يكون عن قصد، بمراجعة مكتوبة وبعد اجتياز كل الاختبارات. **لم يُعتمد أي إصدار أصلي عبر هذا الإجراء حتى الآن.** القواعد الملزمة موجودة في [سياسة تحديث الأصل](../engineering/UPSTREAM-UPDATE-POLICY.md).

## ما المثبّت

كل صورة أصلية مثبّتة بالوسم والبصمة في أربعة ملفات قفل: `lab/distro-image.lock.json` (صورة PostgreSQL من Supabase)، و`lab/images.lock.json` (Auth وPostgREST وPostgreSQL القياسي الذي تستخدمه البيئات الثابتة)، و`lab/storage-image.lock.json` (Storage)، و`lab/studio-image.lock.json` (Studio وpostgres-meta). اطبع المجموعة كاملة وتحقق أن لا شيء منها عائم:

```
/usr/bin/python3 lab/pin_update.py show
/usr/bin/python3 lab/pin_update.py verify
```

## تغيير مكوّن واحد

1. اقرأ ملاحظات الإصدار الأصلية للنسخة المرشحة.
2. حضّر التغيير. يكتب هذا الأمر مدخل مراجعة مؤرخًا تحت `docs/upstream/`، ويسجّل البصمة السابقة تثبيتًا للتراجع، ويغيّر مكوّنًا واحدًا بالضبط:

   ```
   /usr/bin/python3 lab/pin_update.py stage --file lab/images.lock.json --component rest \
       --tag public.ecr.aws/supabase/postgrest:vX.Y --digest sha256:<64 hex> --note "why"
   ```

3. أكمل مدخل المراجعة: ما الذي تغيّر، وأي أجزاء من صباربيز يمسّها، والتغييرات الكاسرة والترحيلات، وقرار الاعتماد أو التأجيل.
4. اجتز بوابة الاعتماد: مجموعتا اختبارات Python وBun كاملتين، والفحوص الحية للتكامل مع النسخة الجديدة. لا اعتماد بلا اختبارات.
5. اعتمد مكوّنًا واحدًا في كل مرة، فيدل أي فشل على تغيير إصدار واحد.

## التراجع عن تثبيت

أعد التثبيت السابق المسجّل في مدخل المراجعة وانشره في إصدار جديد، فتصل إليه التثبيتات عبر `lab/upgrade.py`. إذا رحّلت النسخة الأحدث البيانات، فقد يحتاج التراجع إلى ترحيل بيانات خاص به؛ سجّله في المدخل نفسه.

## حاويات قواعد البيانات حالة خاصة

لا يعيد التشغيل إنشاء حاوية قاعدة بيانات أبدًا كترقية ضمنية. حاوية القاعدة المُدارة مثبّتة بهويتها الدقيقة، واستبدالها (لصورة جديدة مثلًا) يمر عبر `lab/migrate-generation.py`، وهو إجراء بسجل عملية ومختبر ضد الانهيار على بيئات ثابتة مؤقتة. لم يحدث بعد أول تشغيل له تحت إشراف على بيانات محفوظة؛ انظر [الحالة](../reference/status.ar.md).

## الحدود

- لم تُجرَّب أي ترقية على خادم فيه بيانات عملاء حقيقية.
- العودة لا تلغي تغييرًا أجراه Auth أو Storage الأحدث على قاعدة البيانات عند تشغيله. ترحيلات الأصل تضيف إلى المخطط، فيعمل الإصدار السابق عليه عادةً؛ وإن لم يعمل، فاستعد النسخ الاحتياطية المأخوذة قبل الترقية.
- إصدار جديد يفشل بطريقة لا يراها المشرف (يعمل لكنه يسيء التصرف) لا يُعاد وحده. استخدم `rollback`.
